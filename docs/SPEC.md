## 1. Архитектура

```
 Браузер ──► nginx (web) ──► /api/*  ──► workhub-server (Rust, axum) ──► PostgreSQL
    │           └── SPA (SvelteKit, static)          │    ▲
    │                                                │    │ download / callback (JWT)
    └──► ONLYOFFICE Docs (api.js, редактор) ◄────────┘    │
               └──────────────────────────────────────────┘
```

| Компонент | Технология | Назначение |
|---|---|---|
| API | Rust 2021, axum 0.8, tokio, sqlx 0.8 | REST API, права доступа, интеграция с редактором |
| БД | PostgreSQL 16 | Все данные; миграции встроены в бинарник (`sqlx::migrate!`) |
| Хранилище файлов | Локальная ФС за трейтом `BlobStore` | Версии файлов; S3/MinIO — этап 2 |
| Веб-клиент | SvelteKit 3 + Svelte 5 (runes), Vite 8, adapter-static 4 (с итерации 33) | SPA, отдаётся nginx; настройки SvelteKit — в `frontend/vite.config.ts`, общие модули импортируются как `#lib/…` (поле `imports` в `package.json`) |
| Редактор | ONLYOFFICE Docs (Document Server) | Совместное редактирование DOCX/XLSX/PPTX |
| Развёртывание | Docker Compose | db, backend, web, onlyoffice |
| Десктоп | Tauri v2 (этап 3) | Тот же Svelte-UI + синхронизация файлов |

Принятые решения:
- **SPA, а не SSR.** Приложение за логином, SEO не нужно. Статический бандл упрощает развёртывание и позволяет переиспользовать UI в Tauri без изменений.
- **Один бинарник API.** Модули внутри одного процесса. Разделение на сервисы — только при реальной нагрузке.
- **Сырые SQL-запросы (`sqlx::query_as`)** без ORM. Запросы видны целиком, а сборка не требует живой БД.

## 2. Мультитенантность

Модель «общая БД, общая схема». Каждая строка, принадлежащая порталу, содержит `tenant_id`.

- Портал (`tenants`) имеет `slug` — короткий адрес вроде `partner-garant`. При входе пользователь указывает портал, email и пароль.
- Сессия привязана к тенанту. Все запросы API берут `tenant_id` из сессии, а не из параметров клиента.
- Каждый SQL-запрос фильтрует по `tenant_id`. Сквозной тест проверяет, что пользователь чужого портала получает 404 на файлы, папки и проекты.
- Квота хранилища задаётся на портал (`tenants.quota_bytes`, по умолчанию 10 ГиБ) и считается по всем версиям.

**Этап 2:** Postgres Row-Level Security как второй рубеж (`SET LOCAL app.tenant_id` в транзакции запроса, отдельная роль БД без BYPASSRLS); поддомены `{slug}.workhub.example`.

## 3. Аутентификация

| Механизм | Реализация |
|---|---|
| Пароли | Argon2id (`argon2`), вычисление в пуле blocking-потоков; минимум 10 символов |
| Сессии | Случайный 256-битный токен. В БД хранится только SHA-256; срок жизни 7 суток |
| Транспорт | Cookie `wh_sid`: HttpOnly, SameSite=Lax, Secure — при HTTPS. Для Tauri и интеграций — `Authorization: Bearer` |
| 2FA | TOTP (RFC 6238, SHA-1, 6 цифр, 30 с), QR-код для приложения |
| Двухшаговый вход | Пароль даёт сессию `pending_mfa` (5 минут, только `/auth/totp/verify`). Верный код выдаёт новую активную сессию — защита от фиксации сессии |
| Перебор кода | Не более 5 неверных кодов на одну попытку входа, затем сессия удаляется |
| Тайминг | Для несуществующего пользователя пароль проверяется против фиктивного хеша |
| Смена пароля | Завершает все сессии пользователя |
| Блокировка | Деактивация пользователя удаляет его сессии |
| CSRF | SameSite=Lax + JSON-тела запросов; API и UI на одном origin |

**Этап 2:** rate-limit входа по IP и аккаунту (`tower_governor`), шифрование `totp_secret` ключом из KMS/env, резервные коды 2FA, приглашения по email, сброс пароля, OIDC/LDAP.

## 4. Роли и права доступа

### Роли портала
| Роль | Возможности |
|---|---|
| owner | Всё; нельзя понизить или заблокировать |
| admin | Полный доступ ко всем документам и проектам, управление пользователями |
| member | Работа в своих папках, общих документах и проектах, где он участник |
| guest | Только чтение и комментирование того, чем поделились; нет личной папки |

### Документы: эффективный доступ
`None < Read < Comment < Edit < Full` — берётся максимум из следующих источников:

1. admin/owner → Full;
2. владелец файла или любой папки в цепочке предков → Full;
3. корень `common` → Edit для сотрудников, Read для гостей;
4. корень `project` → по роли в проекте: manager → Full, member → Edit, viewer → Read;
5. явные права (`shares`) на файл или любую папку-предка — пользователю, его группе или «всем на портале».

Гость никогда не получает больше Comment. Ресурсы без доступа отдают **404, а не 403**, чтобы не раскрывать их существование.

Что даёт каждый уровень:
- **Read** — чтение и скачивание;
- **Comment** — комментарии в редакторе;
- **Edit** — редактирование и загрузка в папку;
- **Full** — переименование, удаление, перемещение и управление доступом.

### Проекты
`viewer < member < manager`. Исполнитель задачи может менять свою задачу даже с ролью viewer.

## 5. Схема данных

См. `backend/migrations/0001_init.sql`. Основные таблицы:

- `tenants`, `users`, `groups`, `group_members`, `sessions`, `audit_log`
- `folders` (дерево, `kind`: my | common | project | regular, мягкое удаление)
- `files` (текущая версия, `edit_key` — ключ сессии совместного редактирования)
- `file_versions` (каждая версия — отдельный blob, sha256, автор)
- `shares` (folder/file → user | group | everyone, уровень 1–4)
- `projects`, `project_members`, `tasks` (иерархия `parent_id`, вехи `is_milestone`, номер `number`), `task_dependencies` (FS/SS/FF/SF + лаг), `time_entries`
- `task_labels`, `task_label_links`, `task_checklist_items` — метки и чек-листы задач (миграция `0013`, раздел 8л)

Ограничения целостности в БД: уникальность имён в папке (без учёта регистра, только среди неудалённых), `start_date <= due_date`, задача не может зависеть от себя. Циклы в зависимостях проверяются рекурсивным CTE при добавлении связи.

## 6. Интеграция с ONLYOFFICE Docs

### Последовательность
1. Пользователь открывает `/editor/{id}`, SPA вызывает `GET /api/files/{id}/editor`.
2. API проверяет права и формирует конфиг редактора:
   - `document.url` — ссылка `INTERNAL_URL/api/oo/download/{id}?t=<app-JWT, 24 ч>`;
   - `editorConfig.callbackUrl` — ссылка `INTERNAL_URL/api/oo/callback/{id}?t=<app-JWT>`;
   - `permissions` (edit, comment, review, download) — из эффективного доступа;
   - весь конфиг подписывается `DOCS_JWT_SECRET` (поле `token`).
3. SPA загружает `DOCS_PUBLIC_URL/web-apps/apps/api/documents/api.js` и создаёт `DocsAPI.DocEditor`.
4. Document Server скачивает файл по `document.url`.
5. При сохранении Document Server вызывает callback. API проверяет оба JWT: свой токен в URL и токен Document Server (в теле или в `Authorization`). Затем скачивает результат и записывает новую версию.

### Ключ документа (`document.key`)
- **Режим редактирования.** Все пользователи, открывшие файл, получают общий `files.edit_key`, и их сессии объединяются в совместное редактирование.
- **Статус 2** (все закрыли редактор, есть изменения): сохраняется новая версия, `edit_key` сбрасывается.
- **Статус 4** (закрыли без изменений): `edit_key` сбрасывается.
- **Статус 6** (принудительное сохранение): сохраняется версия, ключ не меняется — сессия продолжается.
- **Статусы 3 и 7:** ошибка пишется в лог.
- **Режим просмотра:** ключ `{id}-v{version}`, кеш Document Server переиспользуется.
- Callback с чужим или устаревшим ключом игнорируется — защита от записи из старой сессии.
- При ошибке ответ `{"error": 1}`, и Document Server повторит callback позже.

### Форматы
- **Редактирование:** docx, docm, dotx, xlsx, xlsm, xltx, pptx, pptm, potx, odt, ods, odp, csv, txt, rtf.
- **Просмотр:** doc, xls, ppt, pdf, epub, fb2, djvu, xps и др.

Новые документы создаются из встроенных пустых шаблонов (`backend/assets/templates`).

### Сеть (Docker)
| Переменная | Кто обращается | Значение в compose |
|---|---|---|
| `INTERNAL_URL` | Document Server → API | `http://backend:8080` |
| `DOCS_PUBLIC_URL` | браузер → Document Server | `http://localhost:8081` |
| `DOCS_INTERNAL_URL` | API → Document Server | `http://onlyoffice` |

Document Server обращается к приватному адресу контейнера, поэтому в compose включён `ALLOW_PRIVATE_IP_ADDRESS=true`.

### Лицензия
ONLYOFFICE Docs Community распространяется под AGPL v3 и ограничена 20 одновременными подключениями. Для SaaS с внешними клиентами нужна редакция Enterprise/Developer — это вопрос лицензирования, а не кода: API интеграции у редакций одинаковый.

## 7. Проекты и диаграмма Ганта

- **Проект** создаёт собственную корневую папку документов (`kind = project`) с тем же названием; доступ к ней определяется ролями в проекте.
- **Название проекта = «Наименование объекта».** Если в реквизитах портала есть текстовое поле с ключом `object_name` или названием «Наименование объекта» (первое действующее), оно и название проекта — одно значение (`fields::name_def`):
  - правка реквизита переименовывает проект (переносы строк и повторные пробелы сворачиваются в один пробел, длиннее 1000 символов — обрезается);
  - `PATCH /api/projects/{id}` с `name` записывает то же значение в реквизит;
  - при создании проекта заполненный реквизит становится названием, а пустой заполняется из названия; в формах создания проекта (в том числе из сделки) одно поле вместо двух;
  - миграция `0014` выровняла существующие проекты: где реквизит заполнен, название взято из него; где пуст — реквизит заполнен названием.
- **Изменение проекта:** руководитель правит на вкладке «Реквизиты» (кнопка «Редактировать»): описание, реквизиты и — если поля «Наименование объекта» нет — название. При переименовании переименовывается и папка проекта, в журнал пишется `project.renamed` (при правке через `PATCH`). Название — от 1 до 1000 символов, «/» и «\\» допустимы; в имени папки они заменяются на «-», имя папки обрезается до 255 байт.
- **Задачи:** статус, приоритет, исполнитель (только участник проекта), даты, % готовности. Статус «выполнена» ставит 100%. Вехи — задачи нулевой длительности.
- **Зависимости:** FS/SS/FF/SF с лагом. Связь, создающая цикл, отклоняется. Ганта подсвечивает красным нарушенные FS-связи (последователь начинается раньше окончания предшественника).
- **Ганта** (`frontend/src/lib/Gantt.svelte`) — собственный SVG-компонент без внешних библиотек:
  - масштабы день / неделя / месяц, линия «сегодня»; выходные, праздники и переносы рабочего календаря затенены (праздники — розоватым), у дня — подсказка с названием праздника;
  - перетаскивание полосы сдвигает сроки, перетаскивание правого края меняет длительность (шаг — день). В проекте «в рабочих днях» полоса встаёт на рабочие дни и сохраняет длительность в рабочих днях;
  - изменения сохраняются оптимистично и откатываются при ошибке.
- **Учёт времени** — таймер и записи по задачам, раздел «Отчёты», оплата работы по часам или фиксированная (раздел 8с).

### Планирование графика (`backend/src/scheduling.rs`)

Даты считаются включительно: задача с 1 по 3 число длится 3 дня, а последователь по связи «окончание–начало» может начаться 4-го. Веха — это один день, она может совпадать с днём окончания предшественника.

У проекта есть режим подсчёта дней (`projects.day_mode`):
- **`work` — рабочие дни** (по умолчанию для новых проектов). Длительность, задержка связи (L) и резерв считаются в рабочих днях по рабочему календарю (раздел ниже). Даты начала и окончания задачи не попадают на нерабочие дни: при сохранении начало переносится на ближайший рабочий день вперёд, окончание — на ближайший рабочий день назад (но не раньше начала). Автосдвиг сохраняет длительность в рабочих днях.
- **`calendar` — календарные дни.** Все дни считаются одинаково, даты не переносятся. Проекты, созданные до итерации 18, остались в этом режиме.

Режим переключает руководитель проекта над диаграммой («Рабочие дни / Календарные»). Сами даты задач при переключении не меняются; чтобы снять задачи с нерабочих дней, достаточно «Выровнять по связям» или сдвинуть задачу. В карточке задачи под датами показана длительность («13 раб. дн. · 17 кал. дн.») и предупреждение, если выбран нерабочий день.

Внутри планировщик переводит даты в порядковые номера рабочих дней (`WorkCalendar` в `backend/src/calendar.rs`): начало — первый рабочий день не раньше даты, окончание — последний рабочий день не позже даты. Все формулы ниже работают с этими номерами; в режиме календарных дней номер — просто номер дня.

| Связь | Условие для последователя S (предшественник P, задержка L дней) |
|---|---|
| FS (окончание–начало) | S.начало ≥ P.окончание + 1 + L; для вехи — P.окончание + L |
| SS (начало–начало) | S.начало ≥ P.начало + L |
| FF (окончание–окончание) | S.окончание ≥ P.окончание + L |
| SF (начало–окончание) | S.окончание ≥ P.начало + L |

- **Автосдвиг** (переключатель проекта, включён по умолчанию). При изменении дат задачи или добавлении связи все последователи по цепочке сдвигаются вперёд с сохранением длительности.
  - Задачи никогда не переносятся на более ранние даты.
  - Выполненные задачи не двигаются.
  - Задача без дат пропускается.
  - Пользователь видит список сдвинутых задач.
- **«Выровнять по связям»** устраняет все нарушенные связи проекта разом. Нужно, если автосдвиг был выключен.
- **Критический путь** считается обратным проходом CPM по текущим датам с учётом всех четырёх типов связей:
  - резерв задачи = поздний допустимый срок − текущий срок;
  - задачи с нулевым резервом выделяются красным;
  - отрицательный резерв означает нарушенную связь — она показывается красной стрелкой и счётчиком над диаграммой;
  - резерв выводится в подписи полосы и во всплывающей подсказке.
- **Базовый план** — снимок дат всех задач, сохраняет руководитель проекта. На диаграмме он виден тонкими серыми полосами, в подсказке — отклонение в днях, над диаграммой — смещение окончания проекта относительно плана.

### Рабочий календарь (итерация 18, C1)

Производственный календарь РФ поставляется с порталом (миграция `0020_work_calendar.sql`, таблица `calendar_days`) — на 2025–2027 годы по постановлениям Правительства о переносе выходных. Хранятся только дни, отличные от обычной недели «пн–пт рабочие, сб–вс выходные»:

| Вид (`kind`) | Значение | Рабочий? |
|---|---|---|
| `holiday` | нерабочий праздничный день (ст. 112 ТК РФ) | нет |
| `off` | перенесённый выходной | нет |
| `work` | рабочая суббота или воскресенье | да |
| `short` | предпраздничный день, на час короче (может быть и рабочей субботой) | да |

Проверка данных: в каждом из трёх годов 247 рабочих и 118 нерабочих дней, по 4 сокращённых дня; рабочие дни по месяцам совпадают с опубликованными календарями.

- **Изменения портала** (`tenant_calendar_days`) перекрывают поставляемый календарь: корпоративный выходной, рабочий день вместо праздника, сокращённый день. Кнопка «Как в официальном» удаляет изменение. Изменения видны только в своём портале и пишутся в журнал (`calendar.day_set`, `calendar.day_reset`).
- **Год без официальных данных.** Кнопка «Отметить праздники по ТК РФ» добавляет праздники ст. 112 и переносит праздник, выпавший на выходной, на следующий рабочий день (кроме январских — их переносит постановление Правительства, администратор вносит их вручную). Дни, уже отмеченные в календаре, не меняются.
- **Администрирование → Рабочий календарь**: год по месяцам с числом рабочих дней в каждом; сводка — рабочие, выходные и праздничные, сокращённые дни, норма часов при 40-часовой неделе (8 ч × рабочие дни − сокращённые); легенда; нажатие на день открывает выбор вида дня и пояснения. Дни, изменённые на портале, отмечены точкой.
- Интерфейс загружает календарь по годам и держит в памяти (`frontend/src/lib/workCalendar.svelte.ts`): Ганта, карточка задачи и (в будущем) учёт времени F3 и сводный Гант считают по нему рабочие дни.

| Метод и путь | Назначение |
|---|---|
| `GET /api/calendar?year=` | Особые дни года, рабочие дни по месяцам, итоги, норма часов, `official` — есть ли официальный календарь, `official_years` |

Раздел `/admin` доступен владельцу и администраторам портала.

| Пользователи | Поиск; создание с генерацией пароля; смена роли; блокировка; сброс пароля (завершает сеансы); сброс 2FA; завершение всех сеансов |

**Правила ролей:**
- администраторов назначает и управляет ими только владелец;
- владельца нельзя понизить, заблокировать или сбросить ему пароль;
- изменить собственную роль или статус нельзя;
- действия над своей учётной записью — только через профиль.

### Реквизиты проектов

Администратор задаёт набор типизированных полей, которые заполняются в каждом проекте. Параметры поля:
- **название**;
- **системный ключ** `key` — генерируется транслитерацией из названия, например `nomer_dogovora`;
- **раздел** — группа на форме;
- **тип**;
- **подсказка**;
- **флаги**: «обязательный», «показывать в карточке проекта», «архив».

Таблицы: `project_field_defs`, `project_field_values` (значение хранится в JSONB).

| Тип | Хранение | Проверка на сервере |
|---|---|---|
| Строка / многострочный текст | string | до 500 / 5000 символов |
| Число | number | принимает «1 250 000,50» |
| Дата | `YYYY-MM-DD` | корректная календарная дата |
| Список значений | string | значение из списка вариантов |
| Сотрудник | UUID | пользователь этого портала |
| Флажок | bool | — |
| Контрагент из CRM | `{"id", "name", "inn"}` | `id` — контрагент этого портала (наименование и ИНН берутся из карточки); без `id` — введённое вручную наименование до 500 символов |

Поведение:
- **Обязательные реквизиты** проверяются при создании проекта и при каждом сохранении: итоговое состояние не может их не содержать. Форма создания проекта показывает только обязательные поля; остальные открываются флажком «Заполнить все».
- **Архив.** Поле скрывается из форм, но значения сохраняются и видны в карточке. **Удаление** удаляет и все значения.
- **Смена типа** запрещена, если у поля уже есть значения.
- **Типовой набор** «обследование и проектирование» содержит 15 полей: шифр, вид работ, стадия, наименование и адрес объекта, кадастровый номер, заказчик и его ИНН, номер, дата и стоимость договора, срок сдачи, ГИП, ГАП, «требуется экспертиза». Набор применяется повторно без дублей.
- **Кто редактирует.** Значения меняют руководители проекта и администраторы портала. Видят их все участники проекта.
- **Заказчик из справочника.** Первое действующее поле типа «Контрагент из CRM» считается заказчиком проекта: при сохранении оно синхронизирует связь `projects.company_id` (выбран контрагент — проект связан; введено вручную или очищено — связи нет). В типовом наборе это поле «Заказчик»; миграция `0009` перевела в этот тип существующие поля `client`, сохранив значения и связи. В форме поле ищет по наименованию и ИНН, может добавить новый контрагент в справочник, при выборе заполняет «ИНН заказчика». Пользователи без CRM вводят наименование текстом. В шаблонах документов подставляется наименование. При удалении контрагента наименование в реквизитах сохраняется, связь снимается.
- **Где отображаются.** Шифр проекта показывается в заголовке и на карточке. Поля с флагом «в карточке» — набор столбцов и полей карточки в списке проектов **по умолчанию** (пока сотрудник или администратор не настроили свой, см. «Список проектов»), а также плитки «паспорта» проекта. Поиск в списке идёт по всем реквизитам.
- **Вкладка «Реквизиты» — «паспорт проекта»** (`lib/RequisitesView.svelte`):
  - поля с флагом «в карточке» — плитки ключевых показателей в верхнем ряду (на телефоне — по две в ряд);
  - остальные — карточки разделов с иконкой по названию раздела (объект, договор, участники, общие сведения); карточки раскладываются в две колонки без пустот;
  - пустые поля не занимают строк: в конце раздела строка «Не заполнено: … · заполнить» (ссылка открывает редактор, видна тем, кто может править);
  - оформление значений по типу: контрагент — ссылка на карточку CRM и ИНН под ним; сотрудник — аватар с инициалами; флажок — плашка «Да/Нет»; дата — «через N дней»; для срока (в названии или ключе «срок», «сдач», «deadline») — цвет «скоро» (≤ 14 дней) и «просрочено», полоса прошедшей части срока от самой ранней из дат проекта (начало проекта, дата договора); суммы (число с «руб», «стоимость», «сумма», «цена», «аванс» в названии) — «4 850 000 ₽»; коды без пробелов с цифрами (шифр, ИНН, кадастровый номер, номер договора) — моноширинным шрифтом с кнопкой «Копировать»; адрес — ссылка «на карте» (Яндекс Карты);
  - «Наименование объекта» в паспорте не повторяется — это заголовок страницы. Архивные поля показываются, только если заполнены, с пометкой «архив».
- **Задел на будущее.** Ключи реквизитов предназначены для подстановки в шаблоны документов (`{{project.code}}`) — это этап 2.

### Единый стиль интерфейса (итерация 17, направление «Строгий»)
Основа — дизайн-токены в `frontend/src/app.css`; страницы используют общие классы, а не собственные копии стилей.
- **Палитра:** нейтральный серый фон `#f6f7f9`, белые поверхности, тонкие рамки `#e4e7ec` / `#d0d5dd`, текст в три уровня (`--text`, `--text-2`, `--text-3`), дополнительная поверхность `--surface-3` для подложек; акцент — фирменный цвет портала. Тёмная схема переопределяет те же токены.
- **Формы:** скругление 7 px (карточки — 10 px), лёгкая тень `--shadow`, кольцо фокуса `--ring` вокруг полей и кнопок; кнопки и поля высотой 36 px (`.btn.sm` — 30 px), на страницах входа — 42–44 px.
- **Иконки** Lucide с единой толщиной линии 1,6 px (правило для `svg.lucide-icon`), в меню — 19 px.
- **Общие элементы:** `.seg` — сегментный переключатель (белая «таблетка» на серой подложке) для видов и периодов; `.tabs-line` — вкладки с подчёркиванием; `.chip-icon` — иконка в цветном квадрате (плитки показателей); `.with-icon` — поле со значком слева; `.empty-state` и компонент `EmptyState` — пустые состояния с иконкой в круге, текстом и кнопкой; таблицы `table.list` с серой шапкой без заглавных букв.
- **Каркас:** боковое меню с полосой у активного пункта и счётчиками; на телефоне — верхняя полоса с названием портала и кнопкой меню.
- **Администрирование:** слева — меню разделов по группам с иконками (Портал: обзор, портал и регистрация, модули, оформление, рабочий календарь, почта; Люди: пользователи, группы; Данные и документы: реквизиты проектов, шаблоны, организация; Безопасность: резервные копии — только системный портал, журнал действий), справа — раздел с заголовком. На узких экранах меню становится горизонтальной лентой.
- **Вход и регистрация:** слева — панель фирменного цвета с геометрическим узором, названием портала, подзаголовком и тремя возможностями портала (без них — если загружен свой фон); справа — форма «Вход на портал» в карточке с фирменной полосой сверху на светлой подложке с сеткой точек (в тёмной схеме — тёмные аналоги; на телефоне карточка во всю ширину), иконки в полях. Если портал уже известен (ссылка `?portal=` или прошлый вход) и его оформление найдено, вместо поля «Портал» показывается метка с названием портала, под карточкой — «Другой портал? Сменить» (возвращает поле) и «Создать портал». Внизу всех страниц входа — строка «Защищённое соединение · данные хранятся на сервере компании». Поля, которые браузер заполнил сам (сохранённые логин и пароль), подсвечиваются светлым янтарём (`--fill-bg`, `--fill-border` в `app.css`, свои значения для тёмной схемы) вместо голубого цвета браузера — во всём портале. Знак по умолчанию — облако (так же favicon); имя продукта в интерфейсе — CLOUD-PROJECT.

### Оформление портала

Хранится в таблице `tenant_branding`, по одной строке на портал. Если строки нет, действуют стандартные значения.

- **Тема.** Фирменный цвет задаётся одной CSS-переменной `--brand`. Остальные акцентные оттенки выводятся через `color-mix()` отдельно для светлой и тёмной схемы. Цвет текста на акцентных элементах (белый или тёмный) выбирается автоматически по контрасту WCAG. Редактор показывает коэффициенты контраста и предупреждает о слишком светлом цвете.
- **Боковая панель:** светлая, тёмная или фирменного цвета. Для тёмных логотипов есть опция белой подложки.
- **Цветовая схема** (как в системе / всегда светлая / всегда тёмная) и **скругления** задаются атрибутами `data-theme` и `data-corners`.
- **Шрифт портала**: по умолчанию Inter (миграция `0019` перевела на него и порталы со «системным» шрифтом); можно выбрать системный или один из шрифтов Google Fonts с кириллицей (Roboto, PT Sans, Open Sans, IBM Plex Sans, Montserrat, Golos Text, Manrope, Onest, Noto Sans); загружается только выбранный. Размер основного текста — 13, 14 или 15 px. Без доступа к fonts.googleapis.com показывается системный шрифт.
- **Фон страницы входа**: изображение до 3 МБ (JPEG, WebP, PNG, SVG) вместо фирменного градиента. Белую подложку под логотипом на странице входа можно отключить (по умолчанию включена).
  - **Подложка** под прозрачным изображением (PNG/SVG с альфа-каналом): фирменный градиент, светлая (`#f4f6f9`), белая или произвольный цвет `#rrggbb` (`login_bg_base`).
  - **Тон фона** (`login_bg_tone`): «тёмный» — светлый текст и затемнение фона; «светлый» — тёмный текст и иконки (смесь фирменного цвета с тёмно-синим) и осветление фона белой вуалью. Выбор светлой или белой подложки сам переключает тон на светлый.
  - Степень затемнения/осветления 0–85 %. Предпросмотр в настройках показывает итоговое сочетание.
- **Страница входа** подхватывает оформление по адресу портала. Ссылка `…/login?portal=<slug>` открывает её уже оформленной.
- **Логотип и значок:**
  - форматы PNG, JPEG, WebP или SVG, до 512 КБ;
  - тип определяется по содержимому файла, а не по заявленному браузером;
  - SVG со скриптами, обработчиками событий, `foreignObject` или внешними ссылками отклоняется;
  - файлы отдаются с заголовками `Content-Security-Policy: sandbox` и `nosniff` и кешируются навсегда по номеру версии;
  - значок становится favicon портала.

| `{{project.<ключ>.short_name}}`, `.full_name`, `.position`, `.name_genitive`, `.name_dative`, `.nrs`, `.qual_cert`, `.power_of_attorney`, `.phone` | Для реквизита-сотрудника (например, ГИП): данные из его карточки — фамилия с инициалами, ФИО, должность для документов, падежи, НРС, аттестат, доверенность, телефон |
| `{{portal.name}}` | Название организации |
| `{{date}}`, `{{date_long}}`, `{{year}}` | Дата по часам пользователя: 10.11.2026 / 10 ноября 2026 г. / 2026 |
| `{{user.name}}`, `{{user.email}}` | Кто сформировал документ |

Справочник меток с копированием в один клик показан рядом со списком шаблонов.

**Другие написания.** Реквизит проекта пишется `{{project.ключ}}`, но `{{ключ}}` и `{{project_ключ}}` тоже понимаются (например, `{{project_chief_engineer}}` = `{{project.chief_engineer}}`). Встроенные метки (`{{date}}`, `{{year}}` и т. п.) важнее реквизита с тем же ключом. Для ненайденной метки страница шаблонов показывает ближайший подходящий ключ (опечатки) и подсказку о правильном написании.

**Движок подстановки** (`backend/src/ooxml.rs`):
- обрабатывает основной текст, колонтитулы и сноски DOCX, общие строки и листы XLSX;
- Word часто разбивает набранный текст на несколько фрагментов (`<w:t>`) из-за проверки орфографии, правок и смены форматирования. Поэтому движок склеивает текст фрагментов, находит в нём метки и записывает значение во фрагмент, где метка начинается. Форматирование этого фрагмента сохраняется;
- многострочные значения (адрес) переносятся разрывами строк;
- XML экранируется, размер обрабатываемых частей ограничен (защита от zip-бомб).

**Проверки и поведение:**
- **При загрузке** файл проверяется: это действительно DOCX или XLSX, размер до 20 МБ. Найденные метки сохраняются; неизвестные (опечатки) подсвечиваются красным.
- **Перед генерацией** пользователь видит список незаполненных реквизитов и может сразу перейти к их заполнению. Пустые метки заменяются пустым текстом.
- **Имя файла** по умолчанию — «Шаблон Шифр». При совпадении добавляется «(2)», «(3)» и так далее.
- **Пример шаблона** — «Титульный лист отчёта» с полями и шрифтом по ГОСТ 7.32 — устанавливается одной кнопкой.
- **Права:** генерировать могут участники проекта с правом редактирования папки; управлять шаблонами — администраторы.

## 8в. Корзина

- **Где.** Удалённые файлы и папки попадают в корзину (пункт меню «Корзина»). Администратор видит всю корзину портала, сотрудник — то, что удалил сам.
- **Что показывается.** Только верхний уровень удалённого: содержимое удалённой папки восстанавливается и удаляется вместе с ней.
- **Восстановление.** Элемент возвращается в исходную папку, если она существует. При совпадении имени добавляется «(восстановлено)». Папку удалённого проекта восстановить нельзя, только удалить.
- **Удаление навсегда.** Удаляются записи, все версии файлов в хранилище и выданные на них права. Есть кнопка «Очистить корзину».
- **Автоочистка.** Раз в час удаляется всё, что лежит в корзине дольше `TRASH_RETENTION_DAYS` (по умолчанию 30 дней).
- **Квота.** Файлы в корзине учитываются в квоте хранилища.

## 8г. Защита входа

Ограничитель с фиксированным окном хранит счётчики в памяти процесса API (`backend/src/ratelimit.rs`):

| Что считается | Лимит по умолчанию | Переменная |
|---|---|---|
| Неудачные входы на одну учётную запись (портал + email) | 8 за 15 минут | `LOGIN_ACCOUNT_LIMIT` |
| Неудачные входы с одного IP | 30 за 15 минут | `LOGIN_IP_LIMIT` |
| Неверные коды 2FA одного пользователя (по всем попыткам входа) | 8 за 15 минут | — |
| Регистрация порталов с одного IP | 10 в час | `SIGNUP_IP_LIMIT` |

- При превышении API отвечает `429 Too Many Requests` с заголовком `Retry-After`. Успешный вход сбрасывает счётчик учётной записи.
- IP клиента берётся из `X-Real-IP`, который выставляет nginx; клиент подделать его не может.
- При нескольких экземплярах API счётчики нужно перенести в Redis (этап 2).

## 8д. CRM

Модуль `backend/src/crm/`, миграция `0005_crm.sql`, интерфейс — раздел «CRM» (`/crm/...`).

### Доступ
- Роль CRM хранится в `users.crm_role`: `none` — нет доступа, `user` — сотрудник, `manager` — руководитель продаж. По умолчанию `user`. Гости в CRM не допускаются.
- Администратор и владелец с ролью, отличной от `none`, имеют права руководителя.
- Видимость контрагента (`visibility`): `all` — все сотрудники с доступом к CRM; `responsible` — ответственный, автор и руководители; `group` — участники группы, ответственный, автор и руководители. Проверка — SQL-функция `crm_company_visible`.
- Изменять карточку может руководитель, ответственный или автор. Сменить ответственного на другого сотрудника может только руководитель.
- Сделка видна, если у неё нет контрагента, если пользователь — её ответственный или если виден её контрагент.

### Контрагенты
- Реквизиты: ИНН (10/12 цифр), КПП, ОГРН/ОГРНИП (13/15), БИК, расчётный и корреспондентский счета. Контрольные числа проверяются на сервере (`crm/validate.rs`) и в форме (`lib/crm/validate.ts`).
- Дубликат — та же пара ИНН + КПП (уникальный индекс, ответ 409). Совпадение ИНН с другим КПП показывается как предупреждение о филиале. Скрытые совпадения сообщаются без названия.
- Импорт: `.xlsx` или `.csv` (UTF-8 или CP1251, разделитель `;` или `,`), до 5000 строк и 10 МБ. Заголовки на русском или английском. Ошибочные строки и дубликаты пропускаются с отчётом.

### Сделки
- Этапы настраиваются руководителем (`kind`: `open`, `won`, `lost`; вероятность; цвет; порядок). Должен существовать хотя бы один этап каждого типа. Этап со сделками удалить нельзя.
- Смена этапа пишет системную запись в ленту. Переход на `won`/`lost` ставит `closed_at`, возврат в `open` его снимает.
- Канбан показывает открытые сделки и закрытые за последние 30 дней; взвешенная сумма считается по вероятности этапа.

### Связь с проектами
- `projects.company_id`, `projects.deal_id`. Из сделки создаётся проект: заказчик, ИНН и стоимость договора подставляются в реквизиты `client`, `client_inn`, `contract_amount`, если такие поля настроены. Ответственный по сделке становится руководителем проекта.
- Руководитель проекта может привязать заказчика вручную; реквизиты заказчика обновляются из карточки.

### Лента взаимодействий
Типы: заметка, звонок, встреча, письмо, системное событие. Запись привязывается к контрагенту, сделке и (необязательно) контактному лицу. Удалить запись может её автор; системную — руководитель.

### API
| Метод | Назначение |
|---|---|
| `GET/POST /api/crm/companies` · `GET/PUT/DELETE …/{id}` | Контрагенты (список с фильтрами `q`, `tag`, `responsible_id`) |
| `GET /api/crm/companies/check-inn` · `POST /api/crm/companies/import` | Проверка дублей, импорт |
| `GET/POST /api/crm/contacts` · `PUT/DELETE …/{id}` | Контактные лица |
| `GET/PUT /api/crm/stages` | Этапы воронки |
| `GET/POST /api/crm/deals` · `GET/PATCH/DELETE …/{id}` | Сделки |
| `GET/POST /api/crm/deals/{id}/project` | Данные для проекта и создание проекта из сделки |
| `POST /api/crm/activities` · `DELETE …/{id}` | Лента взаимодействий |
| `PUT /api/projects/{id}/company` | Заказчик проекта |

## 8е. Почта, приглашения и восстановление пароля

Модули `backend/src/mail.rs` и `backend/src/accounts.rs`, миграция `0006_mail.sql`.

### Почтовый сервер
- У каждого портала может быть свой SMTP-сервер (Администрирование → Почта): адрес, порт, защита (`tls` — SSL/TLS, обычно 465; `starttls` — обычно 587; `none`), логин, пароль, адрес и имя отправителя, адрес для ответа.
- Пароль SMTP хранится зашифрованным (AES-256-GCM, ключ выводится из `APP_SECRET`) и никогда не возвращается в API. Смена `APP_SECRET` делает сохранённые пароли нечитаемыми — их нужно ввести заново.
- Если свой сервер портала выключен, используется общий сервер системы из переменных `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURITY`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_FROM`, `SMTP_FROM_NAME`. Если нет ни того ни другого, письма остаются в очереди с пометкой «почтовый сервер не настроен».
- Защита от SSRF: сервер портала не может находиться во внутренней сети (loopback, частные диапазоны, link-local, CGNAT). Для разработки проверку отключает `SMTP_ALLOW_PRIVATE=true`. Общий сервер системы не проверяется.
- Ссылки в письмах строятся от `PUBLIC_URL`, а не от заголовков запроса (защита от подмены Host).

### Очередь писем
- Письма пишутся в `mail_outbox` и отправляются фоновым обработчиком сразу и затем раз в 15 секунд. Пакет сообщений «арендуется» (`FOR UPDATE SKIP LOCKED`), поэтому несколько экземпляров сервера не отправят письмо дважды.
- Ошибка доставки — повтор через 1, 5, 15, 60 и 180 минут; после 6 попыток письмо помечается как недоставленное. Администратор видит журнал (последние 100 писем) с текстом ошибки сервера и может повторить отправку вручную.
- Сохранение настроек почты сразу отправляет ожидающие письма. Отправленные и недоставленные письма хранятся 90 дней.
- Тестовое письмо отправляется синхронно с настройками из формы (даже несохранёнными); ответ сервера показывается администратору. Не более 20 проверок в час на портал.

### Одноразовые ссылки
- Таблица `user_tokens` хранит только SHA-256 токена. Новая ссылка того же типа отменяет прежние неиспользованные. Ссылка срабатывает один раз; для заблокированных пользователей и порталов не работает.
- **Приглашение** (7 дней). Администратор приглашает людей по почте — ему возвращаются ссылки, чтобы при необходимости передать их самому (обязательно, если почта не настроена). Пока приглашение не принято, войти нельзя (`users.invite_pending`). Пользователь задаёт пароль и имя и сразу входит. Администратор может отправить приглашение повторно, отозвать его или задать пароль сам — тогда приглашение считается принятым, ссылка отменяется. Подробнее — раздел 8н.
- **Восстановление пароля** (60 минут). Запрос со страницы входа всегда получает одинаковый ответ; поиск учётной записи и отправка письма идут в фоне, поэтому по ответу и времени нельзя узнать, существует ли учётная запись. Ограничения: 3 запроса в час на учётную запись и 10 в час с одного IP. После смены пароля все сеансы завершаются, а владельцу учётной записи приходит уведомление. Двухфакторная защита сохраняется.
- Для приглашённых, но не принявших приглашение пользователей восстановление пароля не выполняется.

### API
| Метод | Назначение |
|---|---|
| `GET/PUT /api/admin/mail` | Настройки почты портала, состояние, журнал отправки |
| `POST /api/admin/mail/test` | Тестовое письмо |
| `POST /api/admin/mail/outbox/{id}/retry` | Повторить отправку |
| `POST /api/users` без `password` | Создать пользователя и пригласить по ссылке (одного; основной способ — `POST /api/admin/invitations`, раздел 8н) |
| `POST /api/admin/users/{id}/invite` | Отправить приглашение повторно |
| `POST /api/public/invite/check` · `POST /api/public/invite/accept` | Проверить и принять приглашение |
| `POST /api/public/password/forgot` | Запросить ссылку для смены пароля |
| `POST /api/public/password/check` · `POST /api/public/password/reset` | Проверить ссылку и задать новый пароль |

Токены передаются в теле запроса, а не в адресе API, чтобы не попадать в журналы веб-сервера.

## 8ж. Уведомления

Модули `backend/src/notify.rs` и `backend/src/comments.rs`, миграция `0007_notifications.sql`. В интерфейсе — колокольчик в меню, раздел «Уведомления» в профиле.

### События
| Вид | Кому | Почта по умолчанию |
|---|---|---|
| `task_assigned` — назначена задача (при создании или смене исполнителя) | исполнителю | да |
| `task_due_soon` — срок сегодня или завтра | исполнителю | да |
| `task_overdue` — задача просрочена | исполнителю | да |
| `task_comment` — комментарий к задаче | исполнителю, автору задачи, прежним комментаторам | нет |
| `task_done` — задача выполнена | автору задачи | нет |
| `checklist_assigned` — поручен пункт чек-листа (при создании пункта или смене исполнителя) | исполнителю пункта | нет |
| `project_added` — добавлен в проект (не при смене роли) | новому участнику | нет |
| `mention` — упоминание через @ в комментарии к задаче или записи CRM | упомянутому | да |
| `file_shared` — открыт доступ к папке или документу | пользователю или участникам группы (доступ «всем» не объявляется) | нет |
| `deal_assigned` — назначен ответственным по сделке | ответственному | да |
| `deal_stage` — сделку перевели на другой этап | ответственному, если перевёл не он | нет |
| `company_assigned` — назначен ответственным за контрагента | ответственному | нет |
| `crm_task_assigned` — поручено дело CRM | исполнителю | да |
| `crm_task_due` — напоминание о деле CRM | исполнителю | да |
| `crm_task_overdue` — дело CRM просрочено | исполнителю | нет |
| `registration_request` — новая заявка на регистрацию в портале (после подтверждения почты заявителем) | администраторам портала; в настройках уведомлений вид виден только им | да |

- Автор действия сам себе уведомлений не получает. Заблокированные и не принявшие приглашение пользователи не получают ничего.
- Упоминание получают только те, кто видит объект: участники проекта и администраторы — для задач; пользователи CRM, которым виден контрагент, — для записей CRM. Упомянутый получает только упоминание, без дублирующего «комментария к задаче».
- Создание уведомления никогда не ломает основное действие: ошибки пишутся в журнал сервера.

### Каналы
- Пользователь включает и выключает каждый вид отдельно: «в приложении» и «по почте» (`notification_prefs`; хранится только отличие от значения по умолчанию). Виды CRM показываются только пользователям CRM.
- **В приложении**: список с отметкой прочитанного, «прочитать все», подгрузка страницами. Новые уведомления приходят без перезагрузки по потоку `GET /api/notifications/stream` (server-sent events); отметка о прочтении синхронизируется между вкладками. После переподключения список перечитывается.
- **По почте**: уведомление, не прочитанное в приложении за `NOTIFY_EMAIL_DELAY_SECS` (по умолчанию 180 с), уходит письмом. Несколько уведомлений одного пользователя собираются в одно письмо со ссылками. Уведомления старше двух суток по почте не отправляются.

### Напоминания о сроках
- Проверка раз в `DUE_SCAN_SECS` (по умолчанию 60 с) по открытым задачам активных проектов с исполнителем. «Сегодня» и «завтра» считаются по часовому поясу портала (Администрирование → Портал, по умолчанию Europe/Moscow). Напоминания отправляются начиная с `DUE_REMINDER_HOUR` (по умолчанию 8:00) местного времени.
- Каждое напоминание приходит один раз на задачу и дату срока (`dedupe_key`). При переносе срока напоминание придёт для новой даты. Просроченные более чем на 7 дней задачи не напоминаются.

### Комментарии к задачам
Обсуждение в карточке задачи. Писать могут участники проекта (кроме наблюдателей) и исполнитель; удалять — автор комментария и руководитель проекта. До 10 000 символов. Ссылки из уведомлений ведут на `/projects/{id}?task={id}` — карточка задачи открывается сразу.

### API
| Метод | Назначение |
|---|---|
| `GET /api/notifications?limit=&before=&unread=` | Список, число непрочитанных |
| `POST /api/notifications/read` `{ids}` или `{all: true}` | Отметить прочитанными |
| `GET/PUT /api/notifications/prefs` | Настройки каналов |
| `GET /api/notifications/stream` | Поток событий (SSE) |
| `GET/POST /api/tasks/{id}/comments` · `DELETE /api/task-comments/{id}` | Комментарии к задаче (`mentions` — список упомянутых) |
| `POST /api/crm/activities` с `mentions` | Упоминание в записи CRM |
| `PATCH /api/admin/portal` с `timezone` | Часовой пояс портала |

Для потока событий в nginx отключена буферизация (`location = /api/notifications/stream`). При нескольких экземплярах API поток нужно перевести на общую шину (например PostgreSQL LISTEN/NOTIFY или Redis) — сейчас события рассылаются внутри одного процесса.

## 8з. Дела CRM

Модуль `backend/src/crm/tasks.rs`, миграция `0008_crm_tasks.sql`. В интерфейсе — раздел «CRM → Дела», блок «Дела» в карточках сделки и контрагента, счётчик у пункта меню CRM.

- **Дело** — следующий шаг по клиенту: звонок, встреча, письмо или прочее (`kind`: `call`, `meeting`, `email`, `todo`). Поля: что сделать, комментарий, дата (по часовому поясу портала), необязательное время, исполнитель, контрагент, сделка, контактное лицо.
- **Привязка.** Дело сделки всегда относится к контрагенту этой сделки. Контактное лицо должно принадлежать контрагенту. Дело может быть и без привязки — например, планёрка отдела продаж.
- **Видимость и права.** Дело видят исполнитель, автор и все, кому виден контрагент; дело без контрагента видят все пользователи CRM. Изменять и удалять дело могут исполнитель, автор, ответственный за контрагента и руководители продаж. Исполнителем можно назначить только пользователя CRM, которому виден контрагент.
- **Напоминания** (вид уведомления `crm_task_due`): для дела со временем — за 15 минут до него; для дела без времени — утром в день срока, начиная с `DUE_REMINDER_HOUR`. Просроченное дело (`crm_task_overdue`) напоминается один раз на дату, не дольше 7 дней. При переносе срока или времени придёт новое напоминание. Поручение дела другому сотруднику — уведомление `crm_task_assigned`. Проверка выполняется раз в `DUE_SCAN_SECS` (по умолчанию 60 с).
- **Выполнение.** Отметка «выполнено» с необязательным итогом записывает в историю взаимодействий сделки или контрагента запись соответствующего типа: «<что сделать>: <итог>». Повторная отметка дубля не создаёт; дело можно вернуть в работу. После выполнения интерфейс предлагает запланировать следующий шаг.
- **Следующий шаг в воронке.** На карточке сделки в канбане — ближайшее открытое дело и его срок (просроченное выделено); у сделки без дел — «нет следующего шага».
- **Раздел «Дела»** группирует открытые дела: просрочено, сегодня, завтра, на неделе, позже. Есть переключатель «Мои / Все», фильтр по сотруднику (для руководителей) и список выполненных.

| Метод | Назначение |
|---|---|
| `GET /api/crm/tasks?scope=&status=&company_id=&deal_id=&assignee_id=` | Список дел и «сегодня» по часовому поясу портала |
| `GET /api/crm/tasks/summary` | Мои просроченные и сегодняшние дела (счётчики меню) |
| `POST /api/crm/tasks` · `PATCH/DELETE /api/crm/tasks/{id}` | Создать, изменить (в т. ч. `done`, `result`, `assignee_id`), удалить |

## 8и. Документы продаж

Модули `backend/src/crm/documents.rs`, `backend/src/money.rs`, миграция `0010_sales_documents.sql`. В интерфейсе — блок «Документы» в карточке сделки, вкладка «Документы» контрагента, «Администрирование → Организация» и вкладка «Документы продаж» в шаблонах.

### Реквизиты организации
Таблица `tenant_requisites`: полное наименование, ИНН, КПП, ОГРН, адреса, контакты, руководитель и его должность, главный бухгалтер, банк, БИК, расчётный и корреспондентский счета, ставка НДС по умолчанию. ИНН, ОГРН, БИК и ключи счетов проверяются так же, как у контрагентов. Краткое наименование — название портала.

### Шаблоны
- У шаблона есть назначение (`scope`): `project` — документы проекта (метки реквизитов проекта), `sales` — документы продаж. Шаблон продаж относится к одному виду: `quote` (КП), `contract` (договор), `invoice` (счёт), `act` (акт). Шаблоны продаж не используются в проектах, и наоборот.
- Метки документов продаж: `doc.*` (номер, дата, дата прописью, предмет, сумма, сумма прописью, сумма без НДС, ставка и сумма НДС, строка про НДС, договор-основание, «действует до»), `client.*` (реквизиты контрагента), `org.*` (реквизиты организации), `contact.*`, `deal.*`, `project.*` (если по сделке создан проект), а также `date`, `user.*`.
- Образцы (кнопка в админке): коммерческое предложение, договор подряда, счёт на оплату, акт выполненных работ. Генератор образцов — `scripts/make_sales_templates.py`.

### Суммы и НДС
- Сумма документа — с НДС. Ставки: без НДС, 0, 5, 7, 10, 20, 22%. НДС выделяется из суммы: `сумма × ставка / (100 + ставка)`, с округлением до копеек.
- Сумма прописью — по правилам русского языка (род, склонения): «Один миллион двести двадцать тысяч рублей 00 копеек».

### Нумерация
- Формат номера для каждого вида задаёт администратор: `{n}` — порядковый номер, `{n:3}` — с ведущими нулями, `{yyyy}`, `{yy}`, `{mm}`. По умолчанию: КП — `КП-{n}/{yy}`, договор — `{n}-{yy}`, счёт и акт — `{n}`.
- Счётчик ведётся по виду и календарному году (`crm_doc_counters`), с 1 января начинается заново. Можно задать следующий номер — например, чтобы продолжить нумерацию из бухгалтерской программы.
- Номер можно ввести вручную. Номер уникален в пределах вида и года; аннулированный документ освобождает номер.

### Формирование и реестр
- Документ формируется из сделки с контрагентом; формировать могут те, кто может изменять сделку. Задаются вид, шаблон, дата, номер (по умолчанию — следующий), предмет (по умолчанию — название сделки), сумма (по умолчанию — сумма сделки), НДС (по умолчанию — ставка организации), основание для счёта и акта (договор этой сделки).
- Файл сохраняется в папку контрагента с именем вида «Счёт № 1 от 10.11.2026.docx», в историю сделки пишется запись. Если какие-то метки остались пустыми, пользователь видит их список.
- Реестр `crm_documents`: вид, номер, дата, контрагент, сделка, основание, предмет, сумма, НДС, статус (`draft` — черновик, `sent` — отправлен, `signed` — подписан, `cancelled` — аннулирован), файл, шаблон.

### Папка контрагента
У каждого контрагента — своя корневая папка вида `crm` (создаётся при первом документе или по кнопке «Папка»). Доступ к ней определяется видимостью контрагента в CRM: руководители продаж, ответственный и автор карточки получают полный доступ, остальные, кому виден контрагент, — редактирование; остальным папка не видна. Владелец папки — владелец портала, поэтому смена ответственного не оставляет доступ у прежнего.

## 8к. База знаний, чаты, команда, финансы

### База знаний
Дерево страниц портала. С итерации 27 текст — в визуальном редакторе «как Word» (раздел 8ц); страницы на Markdown переведены автоматически. На странице показываются путь, «Создана · Обновлена», вложенные страницы.
- Видят и редактируют все сотрудники; гостям раздел недоступен. В архив убирает автор или администратор, вместе с вложенными страницами (раздел 8ц).
- Защита от одновременной правки: сохранение с устаревшей версией отклоняется (409) с именем того, кто изменил страницу; можно сохранить поверх.
- Перемещение с проверкой циклов.
- Поиск: полнотекстовый по-русски (стемминг, веса: название выше текста) с фрагментом совпадения и поиск по части названия.

### Чаты
- Канал проекта создаётся автоматически; доступ — у участников проекта.
- Групповые чаты: создатель или администратор меняет название и состав; участник может выйти; чат без участников удаляется.

- Изменить можно только своё сообщение; удалить — своё или любое (администратор). Удаление мягкое. Длина — до 10 000 символов, не более 60 сообщений в минуту.

Справочник сотрудников: группы, должность, телефон, почта, число открытых и просроченных задач, активных проектов. Отключённых видит только администратор. Имя, должность и телефон сотрудник меняет сам в профиле.

Раздел «Финансы» — см. раздел 8п. Вкладка «Документы» — реестр документов продаж (раздел 8и) за период (месяц, квартал, год, прошлый год, всё время, произвольный), с фильтрами по виду, статусу и тексту. Показатели: договоры, выставленные счета, закрыто актами, счета без актов; график счетов и актов по месяцам; смена статуса прямо в реестре; выгрузка в CSV; у счетов — сколько оплачено. Доступ к вкладке — по правам CRM.

## 8л. Все задачи и карточка задачи

Модуль `backend/src/task_board.rs`, миграция `0013_task_board.sql`. В интерфейсе — раздел «Задачи» (`/tasks`) и общая карточка задачи `frontend/src/lib/tasks/TaskCard.svelte`, которая открывается из раздела, из проекта и по ссылкам уведомлений.

### Номер задачи
- Сквозной по порталу: `#1`, `#2`, … Счётчик — `tenants.task_seq`; номер выдаёт триггер `tasks_number` при вставке. Счётчик блокируется на время вставки, поэтому одновременные задачи получают разные номера. Номер не переиспользуется после удаления задачи.
- Существующие задачи пронумерованы миграцией по дате создания.
- Поиск в разделе понимает номер: «#234» или «234».

### Раздел «Все задачи»
- Задачи всех проектов, где пользователь — участник (администратор портала видит все проекты). По умолчанию только активные проекты; флажок «Закрытые проекты» добавляет приостановленные и закрытые.
- Виды:
  - **Список** — строки с колонкой проекта; группировка по статусу, исполнителю или проекту; сортировка по порядку, сроку, приоритету, номеру, названию; смена статуса и отметка о выполнении прямо в строке.
  - **Календарь** — месяц с понедельника; задача стоит в день срока (без срока — в день начала); цвет полосы — приоритет, точка — первая метка; просроченные выделены красным. Задачи без дат — кнопкой «Без срока: N».
  - **Гант** — сводная диаграмма с заголовком-строкой для каждого проекта и связями внутри проектов; сроки можно двигать в проектах, где пользователь не наблюдатель (или в своих задачах).
- Фильтры (на сервере): проекты, участники («Я», «Без исполнителя», сотрудники), метки (любая из выбранных), приоритет, статус (открытые / выполненные / все), текст или номер. Выбранный вид и фильтры запоминаются в браузере.
- «+ Задача» сначала спрашивает проект (если доступных проектов больше одного).
- Канбан-доски нет — исключена из плана по решению 11.11.2026.

### Карточка задачи
- Шапка: номер, проект, плашка приоритета («Высокий» — жёлтая, «Критический» — красная), сроки «таблеткой» (красной при просрочке), метки.
- Поля: название, описание, исполнитель, приоритет, начало, срок, статус, готовность; сохраняются кнопкой «Сохранить». Метки и чек-лист сохраняются сразу.
- **Чек-лист:** пункт до 500 символов, исполнитель (участник проекта) и срок у пункта, отметка прямо в карточке, перестановка перетаскиванием, полоска прогресса «N из M». До 200 пунктов. Отметка запоминает, кто и когда отметил; повторная отметка автора и время не меняет.
- Предшествующие задачи, учёт времени и обсуждение — как раньше (разделы 7 и 8ж).
- В строках списка: номер, плашка приоритета, метки, счётчики чек-листа и комментариев, полоска прогресса (по чек-листу, если он есть, иначе — процент готовности задачи).

### Метки задач
- Общий справочник портала: название до 40 символов (уникально без учёта регистра), цвет `#rrggbb`, порядок. До 200 меток.
- Добавлять метку может любой сотрудник (кроме гостей) прямо в карточке; переименовывать, перекрашивать и удалять — администратор (кнопка «Метки» в разделе). Удаление снимает метку со всех задач.
- Метки проектов (F6) — отдельный справочник, см. раздел 8п.

### Файлы задачи (итерация 19, C3)

Модуль `backend/src/attachments.rs`, таблица `task_attachments` (миграция `0021`). Вложение — связь задачи с файлом папки проекта; сам файл хранится один раз, с версиями и правами как у остальных документов проекта.

- **Загрузка с компьютера** (кнопка «Загрузить» или перетаскивание в блок «Файлы» карточки): файл сохраняется в папке проекта, в подпапке **«Задачи / #N Название задачи»**, и виден на вкладке «Файлы» проекта. Подпапка создаётся при первой загрузке и запоминается у задачи (`tasks.folder_id`); при переименовании задачи имя папки не меняется. Если папка задачи оказалась в корзине, следующая загрузка создаёт новую. Файл с уже занятым именем получает суффикс: «акт (2).pdf».
- **«Из папки проекта»** — выбор уже лежащих файлов с переходом по подпапкам; прикрепить можно только файлы из папки этого проекта, которые пользователь вправе читать. Повторное прикрепление ничего не меняет.
- **В карточке:** имя (документы открываются в ONLYOFFICE, остальное скачивается), размер, кто и когда прикрепил, кнопки «Скачать» и «Открепить».
- **Открепление** снимает связь, файл остаётся в папке. Открепить может тот, кто прикрепил, и руководитель проекта (администратор портала).
- **Корзина.** Вложение файла, который сам или вместе с папкой попал в корзину, скрывается и возвращается при восстановлении (SQL-функция `file_is_live`). Удаление файла навсегда убирает и вложение.
- **Права.** Прикреплять могут те, кто вправе изменять задачу (участники и руководители проекта, исполнитель). Загрузка из карточки не требует отдельного права на папку. До 100 вложений на задачу, до 50 файлов за одно прикрепление.
- **Счётчик** `attachment_count` (скрепка) — в строках задач проекта и раздела «Задачи».
- Журнал: `task.attachment_added`, `task.attachment_removed`.

| Метод | Назначение |
|---|---|
| `GET /api/tasks/{id}/attachments` | Вложения задачи и `can_edit` |
| `POST /api/tasks/{id}/attachments` (multipart) | Загрузить файлы в папку задачи и прикрепить |
| `POST /api/tasks/{id}/attachments/link` `{file_ids}` | Прикрепить файлы из папки проекта |
| `DELETE /api/tasks/{id}/attachments/{file_id}` | Открепить (файл остаётся) |

Карточка `GET /api/tasks/{id}` дополнена полями `attachments` и `can_detach_any`.

### Права
- Изменять поля, метки и чек-лист могут участники и руководители проекта, а также исполнитель задачи (как и раньше для полей задачи). Удалять задачу и менять связи — участники и руководители.
- Исполнитель пункта чек-листа может отметить свой пункт, даже если в проекте он наблюдатель; менять текст и удалять пункт он не может.
- Задачи и пункты чужого портала или недоступного проекта отвечают 404.

**Поведение выключенного модуля**
- `/api/auth/me` возвращает `modules` — список включённых модулей (с учётом зависимостей); при выключенной CRM `crm_role` = `none`. Интерфейс скрывает пункты меню, вкладку «Гант», кнопку «Документ из шаблона», блоки связей и учёта времени в карточке задачи, вид «Гант» в «Задачах», кнопку «Создать проект» в сделке, вкладки «Организация» и «Реквизиты проектов» администрирования. Открытие раздела по прямой ссылке показывает «Модуль отключён».
- Сервер: промежуточный слой на `/api` (`modules::guard`) по пути запроса определяет модуль и при выключенном отвечает `403 {"error": "module_disabled", "module": "<ключ>"}`. Неавторизованный запрос по-прежнему получает 401. Пользователь сессии загружается один раз на запрос (кешируется в расширениях запроса). Создание проекта из сделки требует и CRM, и Проекты.

- Уведомления: виды уведомлений модуля не создаются (`notify` проверяет модуль), не показываются в настройках уведомлений; напоминания о сроках задач и делах CRM не рассылаются (фоновые проверки пропускают порталы с выключенным модулем). Упоминание относится к модулю объекта (задача — Проекты, запись CRM — CRM).
- Данные модуля не удаляются и не меняются; после включения всё доступно как раньше. Напоминание о сроке, пропущенное за время выключения, придёт после включения (если срок ещё в окне напоминаний).

## 8н. Регистрация в портале и приглашения

Модули `backend/src/registration.rs` и `backend/src/accounts.rs`, миграция `0016_registration_invitations.sql`. В интерфейсе: страница `/register` (ссылка «Зарегистрироваться в портале» на странице входа, если регистрация открыта), «Администрирование → Пользователи» с вкладками «Сотрудники · Приглашения · Заявки», «Администрирование → Портал → Регистрация сотрудников».

### Режимы регистрации
| Режим | `tenants.registration_mode` | Что происходит |
|---|---|---|
| Только по приглашению | `off` | Кнопки регистрации нет, `POST /api/public/register` отвечает 400 «регистрация закрыта» |
| По заявке (по умолчанию) | `request` | Заявитель подтверждает почту, заявка уходит администраторам, они принимают или отклоняют |
| Свободно для корпоративной почты | `domain` | Адрес из списка доменов после подтверждения почты сразу становится учётной записью; остальные адреса — заявки. Доступен только при настроенной почте |

Также задаются роль новых сотрудников (сотрудник или гость) и группы, в которые они попадают (`registration_role`, `registration_group_ids`). Домены хранятся в нижнем регистре без «@»; поддомены указываются отдельно.

### Заявка
- Форма: портал, имя, почта, пароль (не короче 10 символов), комментарий для администратора. Пароль выбирает заявитель; до решения он хранится хешем в `registration_requests`, после решения хеш стирается.
- **Подтверждение почты.** Если почта портала настроена, заявка создаётся со статусом `unconfirmed`, заявителю уходит ссылка `/register/confirm/{токен}` (48 часов, хранится SHA-256). Без почты адрес не проверить — заявка сразу `pending` и уходит администраторам (в списке помечена «почта не проверялась»).
- Повторная заявка с тем же адресом заменяет открытую (и отменяет прежнюю ссылку). Неподтверждённые заявки старше срока ссылки + 1 день удаляются.
- **Защита.** Ответ не зависит от того, есть ли уже такая учётная запись: владельцу существующей записи приходит письмо «Вы уже зарегистрированы» со ссылкой на вход. Скрытое поле-ловушка (`website`) — заявки ботов принимаются с обычным ответом и отбрасываются. Ограничения: `SIGNUP_IP_LIMIT` заявок в час с одного IP (по умолчанию 10) и 3 в час на адрес в портале; подтверждение ссылок — 30 в час с IP.
- После подтверждения администраторы получают уведомление `registration_request` (в портале и по почте) со ссылкой на вкладку «Заявки».
- **Принять:** администратор выбирает роль (по умолчанию — из настроек), учётная запись создаётся с паролем заявителя и группами из настроек, заявителю уходит письмо «Заявка одобрена» со ссылкой на вход. **Отклонить:** с необязательной причиной, которая уходит заявителю письмом. Рассмотренные и неподтверждённые заявки за 90 дней видны в истории.
- Если адрес уже занят (например, человека тем временем пригласили), принятие отклоняется с понятной ошибкой.

### Приглашения
- **Несколько адресов сразу** (до 100): каждый с новой строки или через запятую/точку с запятой, в виде `ivan@x.ru`, `Иван Петров <ivan@x.ru>` или `ivan@x.ru Иван Петров`. Без имени временное имя строится из адреса (`ivan.petrov` → «Ivan Petrov»), приглашённый исправляет его при входе.
- Параметры: роль (администратора приглашает только владелец), группы, **проекты с ролью в каждом** (руководитель, участник, наблюдатель), личное сообщение (до 1000 символов). Группы и проекты назначаются сразу: приглашённый виден в участниках проекта, а после принятия оказывается в проектах. Уведомления не принявшему приглашение не создаются.
- В ответе по каждому адресу: `invited` (со ссылкой и признаком отправки письма), `exists` (уже в портале), `already_invited` (уже приглашён — отправьте повторно), `invalid`.
- Письмо: кто приглашает, личное сообщение, список проектов, кнопка «Принять приглашение». Страница приглашения показывает то же: кто пригласил, сообщение, проекты.
- Вкладка «Приглашения»: кого, роль, проекты и группы, кто и когда пригласил, сколько осталось до истечения ссылки (истёкшие отмечены). Действия: отправить снова (новая ссылка, прежняя перестаёт работать), скопировать ссылку, **отозвать** — не принявшая приглашение учётная запись удаляется (если на неё уже что-то ссылается — блокируется), ссылка перестаёт работать, адрес можно пригласить заново.
- Таблица `invitations` (кто пригласил, сообщение) заполняется и при одиночном приглашении через `POST /api/users`.
- Кнопка «Создать с паролем» осталась для случаев, когда пароль передают лично.

### API
| Метод | Назначение |
|---|---|
| `GET /api/public/branding/{slug}` | Добавлено поле `registration_open` |
| `POST /api/public/register` `{tenant, display_name, email, password, comment, website}` | Подать заявку; ответ `{ok, next: "confirm_email" \| "pending"}` |
| `POST /api/public/register/confirm` `{token}` | Подтвердить почту; ответ `{status: "active" \| "pending", tenant_slug, tenant_name}` |
| `GET/PUT /api/admin/registration` | Настройки регистрации (`mode`, `domains`, `role`, `group_ids`), признак настроенной почты, число ждущих заявок |
| `GET /api/admin/registration/requests[?status=all]` | Заявки (по умолчанию — ждущие решения) |
| `POST /api/admin/registration/requests/{id}/approve` `{role?, group_ids?}` | Принять |
| `POST /api/admin/registration/requests/{id}/reject` `{reason, notify}` | Отклонить |
| `GET /api/admin/invitations` | Неотвеченные приглашения |
| `POST /api/admin/invitations` `{emails, role, group_ids, projects: [{project_id, role}], message}` | Пригласить |
| `DELETE /api/admin/invitations/{user_id}` | Отозвать приглашение |

Журнал: `portal.registration`, `registration.applied`, `registration.joined`, `registration.approved`, `registration.rejected`, `user.invited`, `user.invite_revoked`.

Почта при входе и восстановлении пароля теперь сравнивается без учёта регистра (`IVAN@x.ru` = `ivan@x.ru`).

## 8о. Список проектов

Страница «Проекты» (`routes/projects/+page.svelte`, компоненты `lib/projects/`), настройки вида — `backend/src/view_settings.rs`, миграция `0017_view_settings.sql`.

### Вид
- **Сводка** сверху: активные проекты; просроченные и со сдачей в ближайшие 14 дней (нажатие фильтрует список, ещё раз — снимает фильтр); сумма договоров активных проектов — если среди реквизитов есть денежное поле (число с «руб», «стоимость», «сумма»… в названии).
- **Срок проекта** — первый реквизит-дата со «срок», «сдач» или `deadline` в названии или ключе (в типовом наборе — «Срок сдачи по договору»); если он не заполнен — окончание графика задач. Просрочка и «скоро» считаются только у активных проектов.
- **Вкладки статусов** со счётчиками: Все · Активные · Приостановленные · Закрытые (выбор запоминается в браузере).
- **Таблица («Строками»):** столбцы в настроенном порядке, сортировка по любому столбцу (пустые значения — в конце), закрытые проекты приглушены. Оформление значений: срок — метка «20.11 · через 9 дней» (жёлтая при ≤ 14 днях, красная при просрочке), сотрудник — аватар с инициалами, деньги — «1 250 000 ₽» по правому краю, коды — моноширинным шрифтом, прогресс задач — кольцо и «выполнено/всего». Под названием можно выводить один реквизит или описание.
- **Карточки («Карточками»):** цветная полоса сверху (зелёная — в порядке, жёлтая — сдача скоро или проект приостановлен, красная — просрочен, серая — закрыт); в шапке шифр, статус (если не «активный») и срок; название; выбранные поля сеткой 2×2; внизу первый выбранный сотрудник (например, ГИП) и полоса прогресса задач.
- **Группировка** по статусу или по реквизиту-списку, сотруднику, контрагенту, флажку. У группы — число проектов и сумма договоров; группы сворачиваются (запоминается в браузере). Группы-варианты списка идут в порядке вариантов, «Не указано» — в конце.
- На экранах уже 720 px вместо таблицы показываются карточки; остальные виды доступны.

### Виды «По руководителям», «По меткам», «Сводный Гант» (итерация 23, F7)
- **Переключатель видов** справа от вкладок статусов: Строками · Карточками · По руководителям проектов · По меткам (если в портале есть метки) · Сводный Гант. Выбор запоминается в браузере. Сводка, вкладки статусов, фильтр по меткам, «Фильтры» и поиск действуют во всех видах.
- **«По руководителям проектов»:** колонки по ГИПам (участникам проекта с ролью «руководитель»), по алфавиту; проект с несколькими руководителями — в колонке каждого; «Без руководителя» — в конце. В шапке колонки — аватар, число проектов, число просроченных и сумма договоров активных проектов. Карточка: значок, название, метки, статус (если не «активный»), «до <срок>» (жёлтым — скоро, красным — просрочен), прогресс задач. Только просмотр: руководители меняются в проекте.
- **«По меткам»:** колонки по меткам в порядке каталога, «Без метки» — в конце; проект с несколькими метками — в каждой колонке; своя метка колонки на карточке не повторяется. Только просмотр.
- **«Сводный Гант»:** одна строка на проект (группировка — как в списке), масштаб «Недели / Месяцы / Кварталы» (запоминается в браузере); слева — значок, название и руководители (до двух аватаров), справа:
  - полоса от начала первой до окончания последней задачи с долей выполненных задач и подписью «% · дата окончания»; цвет — по состоянию проекта (просрочен — красный, приостановлен — жёлтый, закрыт — серый);
  - вехи (задачи-вехи с датой) — ромбы, выполненные закрашены;
  - срок по договору (если он отличается от окончания графика) — флажок; красный, если проект просрочен или график задач выходит за этот срок;
  - линия «сегодня»; при открытии и смене масштаба шкала прокручивается к сегодняшнему дню;
  - проект без сроков задач — подпись «нет сроков задач». Нажатие на строку открывает проект.
- **«Фильтры»:** руководитель проекта, участник, заказчик (из CRM). Внутри раздела подходит любой выбранный вариант, разделы сочетаются между собой и с фильтром по меткам. Выбранное показывается плашками над списком (✕ — убрать, «Сбросить» — все); выбор запоминается в браузере; варианты, которых больше нет в списке, выпадают сами.
- **Групповые действия** (вид «Строками»): флажки у проектов, которыми пользователь может управлять (руководитель проекта или администратор портала), и «выбрать все» в шапке. Панель снизу: «Сменить статус…», «Добавить метку…», «Снять метку…», «Снять выделение».
  - Сервер: `POST /api/projects/bulk` `{ ids, status | add_label | remove_label }` — одно действие на запрос, до 200 проектов; всё или ничего: если хоть одним проектом пользователь не управляет — 403, неизвестная метка — 400, больше 10 меток у проекта — 400.
  - Уже имеющие этот статус или метку проекты не считаются; ответ — `{ changed }`. В журнал — запись на каждый изменённый проект: `project.status_changed`, `project.label_added`, `project.label_removed` (с отметкой `bulk`).
- **Данные списка:** `GET /api/projects` дополнительно отдаёт у проекта `manager_ids`, `member_ids`, `milestones` (`[{ date, title, done }]`, до 50 вех с датой) и общий список `people` (`{ id, display_name }` участников показанных проектов).

### Настройка полей
- Кнопка **«Поля»**: две вкладки — «Таблица» и «Карточки». Флажками выбираются поля (реквизиты и встроенные: Проект, Статус, Задачи, Сроки по задачам, Описание), порядок меняется перетаскиванием (или Alt+↑/↓ на флажке). «Проект» в таблице обязателен. Для таблицы — выбор строки «Под названием».
- Настройка своя у каждого сотрудника и хранится на сервере (видна на любом компьютере); группировка тоже входит в настройку. Изменения сохраняются автоматически.
- **По умолчанию:** набор, который администратор сохранил кнопкой «Сделать по умолчанию для всех»; если его нет — поля с флагом «в карточке» конструктора реквизитов. «Сбросить» возвращает сотрудника к набору по умолчанию.
- Удалённые и архивные реквизиты из настроек выпадают сами.

### API
| Метод | Назначение |
|---|---|
| `GET /api/view-settings/{key}` | `{value, own, default}`: своя настройка, иначе набор портала по умолчанию, иначе `null` |
| `PUT /api/view-settings/{key}` `{value}` | Сохранить свою настройку (JSON-объект до 16 КБ) |
| `DELETE /api/view-settings/{key}` | Сбросить свою настройку |

## 8п. Финансы: платежи, аналитика, деньги проектов

Модуль `backend/src/finance.rs`, миграция `0018_finance.sql`; интерфейс — `routes/finance` (вкладки), `lib/finance/`, вкладка «Финансы» проекта.

«Сегодня» для просрочки счетов, дней просрочки и плана поступлений считается по часовому поясу портала (как в CRM), а не по UTC; так же — дата и номер CRM-документа по умолчанию.

### Доступ
- Роль `users.finance_role`: `none` (по умолчанию) — нет доступа, `view` — просмотр раздела, `edit` — внесение и изменение любых платежей, статей и срока оплаты. Задаётся в «Администрирование → Пользователи», столбец «Финансы». Администраторы и владелец — всегда `edit`; гости — никогда. `/auth/me` возвращает действующую роль (`none`, если модуль выключен).
- **Руководитель проекта** (роль `manager` в проекте) без финансовой роли видит деньги своего проекта (вкладка «Финансы» проекта, денежные столбцы списка) и вносит, правит и удаляет **расходы** своего проекта. Поступления и чужие проекты ему недоступны.
- Модуль «Финансы» включается отдельно («Администрирование → Модули»); выключен — раздел, вкладка проекта и денежные столбцы скрыты, API отвечает 403 `module_disabled`, данные сохраняются. Привязка к контрагентам из справочника, счета и вкладка «Документы» работают при включённой CRM.

### Платежи
- Поля: поступление или расход; **проведён** (факт) или **план** (этап графика оплат); дата; сумма (с НДС) и ставка НДС (НДС выделяется, как в документах продаж); статья; проект; контрагент (из справочника CRM или введённый текстом); счёт, который оплачивает поступление; комментарий; кто внёс.
- Оплата счёта: при выборе счёта подставляются долг по счёту, контрагент, проект (по сделке счёта) и комментарий «Оплата по счёту № … от …». Расход не может оплачивать счёт.
- Плановый платёж, дата которого прошла, считается просроченным; кнопка «Поступило» в дебиторке переводит его в проведённые сегодняшним числом.
- **Статьи** — справочник портала (`finance_categories`), типовой набор создаётся при первом обращении: поступления — «Оплата по договору», «Прочие поступления»; расходы — «Зарплата», «Субподряд», «Лаборатория», «Командировки», «Офис», «Налоги», «Прочее». Переименование, добавление, архив («Статьи и сроки»); архивная статья не предлагается для новых платежей.
- **Срок оплаты счёта** (`tenant_requisites.invoice_due_days`, по умолчанию 10 дней от даты счёта). Состояние счёта считается по проведённым поступлениям: «выставлен», «оплачен частично», «оплачен», «просрочен».
- Создание, изменение и удаление платежей пишутся в журнал (`finance.payment_*`).

### Раздел «Финансы»
- **Платежи:** период (месяц … всё время, произвольный), фильтры по типу, факту/плану, статье, проекту, тексту (комментарий, контрагент, проект, № счёта); итоги «Поступило / Израсходовано / Разница / Ожидается по плану»; выгрузка в CSV; кнопки «План оплаты», «Поступление», «Расход»; открытие платежа для правки.
- **Аналитика** (по проведённым платежам): поступления, расходы, прибыль и рентабельность за период; ожидается за 30 дней и просрочено по графику; столбчатый график по месяцам или неделям (неделя — с понедельника); кольцевые диаграммы расходов и поступлений по статьям; проекты за период с поступлениями, расходами и результатом.
- **Дебиторка:** долг по счетам и просроченная часть, просрочено по графику оплат; долг по контрагентам (выбор фильтрует счета); неоплаченные счета с долгом, сроком и днями просрочки, кнопка «Оплата»; график оплат — просроченные и ближайшие 30 дней.
- **Документы:** реестр документов продаж (для пользователей CRM).

### Деньги проекта
- **Бюджет** — реквизит проекта «Стоимость работ» (ключ `contract_amount`, иначе первое числовое поле с «руб», «стоимость», «сумма», «цена» в названии), если он заполнен; иначе сумма сделки, из которой создан проект.
- Показатели: оплачено заказчиком (проведённые поступления), остаток к оплате (бюджет − оплачено), в графике оплат и просрочено по графику, расходы, **прибыль по договору** = бюджет − расходы и результат по деньгам = поступления − расходы. Трудозатраты в прибыль войдут вместе с учётом времени (F3).
- Вкладка «Финансы» проекта: показатели с полосами доли бюджета, график оплат, счета по сделке проекта с состоянием и кнопкой «Оплата», список проведённых платежей; кнопки «Этап оплаты», «Поступление» (финансовая роль `edit`), «Расход» (и руководитель проекта).
- **Список проектов (F5):** в «Поля» добавлены столбцы и поля карточки «Бюджет», «Оплачено», «Остаток к оплате» (видны тем, кому доступны деньги проекта), в сводке — плитка «к получению от заказчиков» (остаток по активным проектам).

## 8с. Учёт времени и «Отчёты» (итерация 24, F3)

Модуль `backend/src/time.rs`, миграция `0023_time_tracking.sql`; интерфейс — `lib/time/` (таймер, блок «Учёт времени» карточки задачи), раздел `routes/reports`. Всё работает при включённом модуле «Учёт времени»; гостям недоступно.

### Таймер
- Кнопка в блоке «Учёт времени» карточки задачи: «▶ Начать» (или «Продолжить», если по задаче уже есть записи); пока идёт — «■ 00:12:34». У сотрудника один таймер: запуск на другой задаче останавливает предыдущий и записывает его время.
- Таймер хранится на сервере (`time_timers`, одна строка на сотрудника) — переживает перезагрузку и виден на другом компьютере; интерфейс перечитывает его при возврате в окно и раз в минуту.
- Плашка идущего таймера внизу справа на всех страницах: задача и проект (ссылка на карточку), время, «■» — комментарий (необязательно), «Записать N мин» или «Сбросить» (без записи).
- Остановка: время округляется до минуты (меньше минуты — запись не создаётся), не больше 24 ч на запись; дата — сегодня по часовому поясу портала; источник записи — «таймер».

### Записи времени
- Вручную: дата, длительность («1:30», «1,5 ч», «90 мин», «2ч 15м»; число до 12 — часы, больше — минуты), комментарий. Писать время могут участники проекта (не наблюдатели); задним числом — без ограничений.
- В карточке задачи — записи по дням (последние 5 дней, «Ещё N дн.»), у каждой: сотрудник, время, «таймер», комментарий, ставка на момент записи (видят администраторы и финансисты).
- Свою запись можно изменить и удалить; руководитель проекта и администратор — любую запись проекта. В журнал: `time.updated` (было/стало), `time.deleted`.

### Оплата работы задачи
- Для каждой задачи — «По часам» (по умолчанию) или «Фикс. за объём» с суммой. Видят руководители проекта, администраторы и финансисты; меняют руководители проекта, администраторы и финансисты с правом «изменение». В журнал — `task.pay_changed`.
- **По часам:** трудозатраты = Σ минут × ставку сотрудника, **запомненную в записи** при её создании. Изменение ставки прошлые записи не пересчитывает; записи без ставки в деньгах не учитываются (карточка показывает, сколько времени без ставки).
- **Фикс. за объём:** сумма засчитывается в трудозатраты, когда задача выполнена (дата выполнения `tasks.done_at` ставится триггером при переходе в «Выполнено» и снимается при возврате); до этого — «ожидается». Время по такой задаче учитывается в часах, но не в деньгах.
- **Финансы проекта:** плитка «Трудозатраты» (начислено; «ещё ожидается» — фикс. оплата невыполненных задач). Прибыль по договору = бюджет − расходы − трудозатраты (начисленные и ожидаемые); «по деньгам сейчас» = оплачено − расходы − начисленные трудозатраты.

### Ставки
- «Отчёты → Ставки» (администраторы и финансисты): стоимость часа каждого сотрудника (`users.hour_rate`). Менять — администраторы и финансисты с правом «изменение». Флажок «Проставлять новую ставку в прошлые записи, где ставки ещё нет» (по умолчанию включён). В журнал — `user.rate_changed`.

### Раздел «Отчёты»
- Период: неделя, месяц, квартал, год (стрелками — соседние, «сегодня» — текущий) или произвольный. Фильтры: сотрудники, проекты, статусы задач. Группировка: по проектам (проект → задача → подзадача → записи), по сотрудникам (сотрудник → проект → задача → подзадача → записи), по задачам (задача → записи). Выбор периода, фильтров и группировки запоминается в браузере.
- Плитки: всего часов, записей и сотрудников; для администраторов и финансистов — стоимость по часам и фикс. оплата задач, выполненных за период. Диаграмма часов по дням (до 62 дней, выходные подсвечены) или по неделям.
- Дерево с итогами на каждом уровне (часы и стоимость), «развернуть всё / свернуть», ссылки на проекты и задачи; для финансистов — таблица «Фиксированная оплата за объём».
- **Кто что видит:** сотрудник — свои часы; руководитель проекта — все часы своих проектов; администраторы и финансисты — всё и деньги. Ставки и деньги остальным не отдаются (ни в отчёте, ни в выгрузке).
- **XLSX** (`GET /api/time/report.xlsx`, те же параметры): листы «Записи» (дата, сотрудник, проект, №, задача, надзадача, часы, комментарий, источник; для финансистов — ставка и стоимость; фильтры и закреплённая шапка), «Итоги» (часы и стоимость по проекту и сотруднику), «Фикс. оплата» (для финансистов). Не больше 20 000 записей за запрос.

## 8т. Экспорт графика (итерация 22, C2)

Модуль `backend/src/gantt_export/` (`mod.rs` — данные и API, `pdf.rs`, `xlsx.rs`, `mspdi.rs`), миграция `0024_gantt_export.sql` (`projects.export_stamp`); шрифт DejaVu Sans Condensed (`backend/assets/fonts`, свободная лицензия) встраивается в PDF подмножеством. Интерфейс — кнопка «Экспорт» на вкладке «Гант» проекта (`lib/projects/GanttExportDialog.svelte`).

### Диалог «Экспорт графика»
- Формат: **PDF** (для печати и заказчика), **Excel**, **MS Project** (XML). Для PDF — лист А3 или А4 альбомный; для PDF и Excel — шкала «Авто / Дни / Недели / Месяцы». Флажки: «Без выполненных задач», «Выделить критический путь», «Базовый план» (если сохранён). Выбор запоминается в браузере.
- **Штамп** (PDF): «Разработал», «Проверил», «ГИП». Подстановка: разработал — кто выгружает, ГИП — реквизит-сотрудник «ГИП» проекта, иначе первый руководитель проекта; исправленные фамилии запоминаются для проекта (участниками и руководителями; наблюдатели выгружают без сохранения).
- Выгружать может любой участник проекта; каждая выгрузка — в журнал (`project.gantt_exported`).

### Строки
- Задачи в порядке дерева (как на графике), с номером строки и номером СДР («2.1»); подзадачи с отступом, группы жирным, вехи «◆». Группа без своих дат охватывает подзадачи. «Без выполненных» убирает выполненные задачи с их подзадачами. API принимает и список `task_ids` (выгрузить только эти задачи).
- Длительность — в рабочих днях по производственному календарю портала (проект в рабочих днях) или в календарных.

### PDF
- Сверху — «КАЛЕНДАРНЫЙ ГРАФИК РАБОТ», шифр и название проекта, «Состояние на <дата>»; слева таблица (№, задача, исполнитель, начало, окончание, длительность, %), справа шкала: месяцы и дни/недели (или годы и месяцы), выходные и праздники затенены (на шкале дней и крупных неделях), линия «сегодня».
- Полосы задач с долей выполнения, группы — тёмные скобки, вехи — ромбы, стрелки связей всех четырёх типов, критический путь — красным, базовый план — серой полоской под задачей. Внизу — легенда.

## 8у. Поиск и быстрое создание (итерация 25, F8 + C5)

Модули `backend/src/search.rs` (API) и `backend/src/textract.rs` (извлечение текста), миграция `0025_search.sql`: расширение `pg_trgm`; вычисляемые столбцы `search` (tsvector, словарь `russian`) с GIN-индексами у проектов, задач, файлов (название), комментариев к задачам, сообщений чатов, контрагентов, контактов, сделок; триграммные индексы названий; таблица `file_texts` (текст текущей версии файла). Интерфейс — `lib/search/` (окно поиска, страница `/search`, меню «Создать»).

### Где ищется
- **Проекты:** название, описание, реквизиты (шифр и др.); в подписи — шифр, заказчик, статус.
- **Задачи:** название, описание, номер (`#234` или `234`); выполненные — ниже; ссылка открывает карточку задачи в проекте.
- **Файлы:** название и текст внутри DOCX/DOCM/DOTX, PPTX, XLSX/XLSM, PDF, TXT/CSV/MD/JSON/XML/LOG (UTF-8 или Windows-1251). Старые DOC, XLS, RTF, изображения, DWG — только по названию. Текст извлекается в фоне сразу после загрузки, создания и сохранения новой версии (из ONLYOFFICE тоже); при запуске сервера и раз в 5 минут дозаполняются файлы без текста или с устаревшей версией. Хранится до 300 тыс. символов на файл.
- **База знаний:** заголовок и текст страниц. **CRM:** контрагенты (краткое и полное название, ИНН), контакты (ФИО, почта, телефон), сделки (название, контрагент). **Комментарии к задачам** и **сообщения в чатах** — по словам. **Сотрудники** — имя, почта, должность.

### Как сопоставляется
- Слова запроса ищутся с учётом русских окончаний и как начала слов («несущ» → «несущих конструкций»), все слова должны встретиться.
- Подстрока названия и кода; опечатки — по сходству триграмм для запросов от 4 символов («обследованее»). Запрос короче 2 символов не выполняется; символы `%` и `_` экранируются.
- Найденное в тексте показывается фрагментом с подсветкой (маркеры `⟦…⟧` в ответе API, в интерфейсе — `<mark>`, без вставки HTML); длинное начало перед совпадением сокращается.

### Права
- Проекты, задачи, комментарии — администраторам и участникам проекта (любая роль). Файлы — в папках проектов, где сотрудник участник; в папках контрагентов, которые ему видны в CRM; в общих документах; свои документы; папки и файлы, к которым дан доступ. Чужие «Мои документы» не ищутся и для администраторов.
- База знаний и сотрудники — не гостям; CRM — по роли в CRM и видимости контрагента (контакты и сделки — по контрагенту, сделка — всегда её ответственному); сообщения — в каналах проектов участникам проекта, в остальных — участникам чата.
- Разделы отключённых модулей (Администрирование → Модули) в поиск не попадают.

### Окно поиска
- Поле «Поиск» вверху бокового меню (в свёрнутом меню — значок, на телефоне — значок в верхней строке), клавиши `Ctrl+K` (`⌘K`) и `/` вне полей ввода.
- По мере ввода — до 5 результатов в каждом разделе с подсветкой; «все» у раздела и «Все результаты по …» ведут на страницу поиска; стрелки и Enter; недавние запросы запоминаются в браузере.

### Страница «Поиск»
- `/search?q&type&project&period` — адрес можно отправить коллеге (результаты у каждого — в пределах его прав). Вкладки разделов (показываются разделы, где что-то нашлось), в разделе — по 30 с «Показать ещё».
- Для задач, файлов, комментариев и чатов — фильтр по проекту и периоду (неделя, месяц, год — по дате изменения или сообщения); на вкладке «Все» с фильтром остаются только эти разделы.

### «+ Создать» (клавиша C)
- Задачу — в выбранном проекте со сроком, затем открывается её карточка (последний проект запоминается); проект и сделку — открывается обычная форма создания; документ Word или таблицу Excel — в «Мои документы», «Общие документы» или корневую папку проекта, затем открывается редактор; страницу базы знаний — открывается новая страница. Пункты зависят от включённых модулей и роли; гостям меню не показывается.
- Ссылки `?new=1` (проекты, сделки, база знаний) открывают форму создания, `?q=` (сотрудники, контакты) заполняет фильтр; параметр затем убирается из адреса.

### API
| Метод и путь | Назначение |
|---|---|
| `GET /api/search?q&type=all\|projects\|tasks\|files\|kb\|companies\|contacts\|deals\|comments\|messages\|people&limit&offset&project&since` | `{ q, groups: [{ type, label, items: [{ type, id, title, subtitle, snippet, url, … }], more }] }`; для `all` — по 5 в разделе (до 20), для одного раздела — по 30 (до 100) со сдвигом |

## 8ф. Список файлов (итерация 25а, по образцу заказчика)

Общий вид списка файлов в «Хранилище» и на вкладке «Файлы» проекта (`lib/FolderBrowser.svelte`), файлы задачи — в том же стиле (`lib/tasks/TaskFiles.svelte`); общие части — `lib/files/` (форматирование, автор, выбор папки). API — `backend/src/file_ops.rs`.

- **Над списком:** путь, поле «Поиск в папке» (мгновенный отбор по названию в открытой папке; если ничего нет — ссылка «Искать во всех файлах портала» на страницу поиска с текстом документов), «Занято N из M» с полосой заполнения (хранилище портала, все версии; на вкладке проекта не показывается), кнопки «Доступ» (для папки), «Создать папку», «Создать ▾» (документ Word, таблица Excel, презентация), «Загрузить».
- **Столбцы:** галочка · Название (с версией «v3», если версий больше одной, и пометкой «редактируется») · Размер (у папок — число объектов внутри) · Изменён («только что», «12 мин назад», «сегодня, 14:05», «вчера, 16:40», дата; полная дата — во всплывающей подсказке) · Автор (аватар и имя). Сортировка по названию, размеру и дате нажатием на заголовок, папки всегда сверху. Шестерёнка в заголовке — какие столбцы показывать (меню поверх страницы, не обрезается краем таблицы); столбцы и сортировка запоминаются в браузере.
- **Строка «На уровень вверх»** — первая в списке вложенной папки; на неё можно перетащить файлы, чтобы поднять их выше.
- **Действия строки** (видны всегда; столбец действий закреплён у правого края и не уезжает при прокрутке таблицы вбок): скачать (папку — архивом), переименовать — прямо в строке (Enter — сохранить, Esc — отменить; у файла выделяется имя без расширения), удалить (в корзину), скопировать ссылку (для сотрудников портала с доступом; публичные ссылки — итерация 26), «⋯» — открыть в редакторе, версии, переместить, копировать, доступ. На телефоне и сенсорных экранах — только «⋯», в нём все действия.
- **Выбор нескольких:** галочки (в заголовке — все), панель «Выбрано: N · размер»: скачать ZIP, переместить, копировать, удалить, снять выделение. Перетаскивание отмеченного перемещает всю выборку.
- **Переместить / копировать** — окно выбора папки: «Все места» (мои документы, общие документы, папки действующих проектов) и вложенные папки, кнопка «Новая папка здесь». Копия получает имя «Имя (копия).docx», затем «(копия 2)»; папка копируется со всем содержимым; копировать папку в неё саму нельзя.
- **Файлы задачи:** имя, размер · когда прикреплён · кто прикрепил (аватар), при наведении — скачать, ссылка, открепить.

## 8х. Ссылки для внешних (итерация 26, F10 + C4)

Модуль `backend/src/public_links.rs`, миграция `0026_public_links.sql` (таблица `public_links`, флаг `tenants.public_links_enabled`). Интерфейс: блок `lib/files/PublicLink.svelte` в окне «Доступ» (файлы и папки) и в окне «Поделиться» (страница базы знаний), публичная страница `/s/{token}`, просмотрщик `/s/{token}/view/{file}`, раздел «Администрирование → Ссылки для внешних».

### Что можно
- Открыть заказчику или подрядчику **файл, папку или страницу базы знаний** без учётной записи — смотреть и скачивать (решение заказчика: только этот режим; загрузки от внешних — не делаем).
- Файлы открываются в ONLYOFFICE только на просмотр (гость «Гость», без правки и комментариев), скачиваются по одному; папка — со всеми вложенными папками, «Скачать всё (ZIP)» или текущую подпапку архивом. Страница базы знаний — только сама страница.
- У ресурса одна действующая ссылка. Адрес — случайный токен из 22 символов: `https://<портал>/s/<токен>`; страницы ссылок закрыты от поисковиков (`noindex`).

### Настройки ссылки
- **Срок:** по умолчанию 30 дней (решение заказчика), можно выбрать дату (ссылка работает по этот день включительно, по часовому поясу портала) или «Бессрочно».
- **Пароль** (необязательно, от 4 символов): страница просит пароль; после ввода выдаётся ключ доступа на эту вкладку браузера. Смена пароля сразу отменяет выданные ключи. 10 неверных попыток за 15 минут — ввод блокируется.
- **Счётчики:** сколько раз открывали (последнее открытие) и сколько скачиваний.
- **Отключить ссылку** — перестаёт работать сразу; новая ссылка получает другой адрес.
- Ссылка перестаёт работать, если файл или папку удалили, истёк срок, ссылку отключили или администратор запретил ссылки на портале.

### Кто управляет
- Файл и папка — сотрудник с полным доступом (владелец, руководитель проекта, администратор); гости — нет. Остальные с доступом видят, что ссылка есть, но не её адрес.
- Страница базы знаний — любой сотрудник (не гость) при включённой базе знаний.
- В списке файлов иконка «ссылка» у человека с полным доступом открывает окно «Доступ» с подсвеченным блоком ссылки; у остальных — копирует внутреннюю ссылку. В меню «⋯» — «Ссылка для сотрудников» и «Ссылка для внешних…».
- **Администрирование → Ссылки для внешних:** все действующие ссылки портала (что открыто, кто выдал, срок, пароль, открытия), отключение любой ссылки, переключатель «Разрешить ссылки для внешних» для всего портала.

### Уведомления и аудит
- При первом открытии ссылки её автор получает уведомление «Вашу ссылку открыли» (колокольчик и почта, вид «Мою ссылку для внешних открыли впервые» в настройках уведомлений).
- Журнал: `link.created`, `link.updated`, `link.revoked`, `link.opened` (первое открытие), `links.settings`.

### API
| Метод и путь | Назначение |
|---|---|
| `GET /api/links?resource_type&resource_id` | `{ link, exists, can_manage, enabled, default_days }`; `link` — только тем, кто управляет |
| `PUT /api/links {resource_type, resource_id, expires_on?, no_expiry?, password?, remove_password?}` | создать ссылку или изменить срок и пароль |
| `DELETE /api/links/{id}` | отключить (автор с правами или администратор) |
| `GET /api/admin/links`, `PUT /api/admin/links/settings {enabled}` | список ссылок портала; разрешить или запретить ссылки |
| `GET /api/public/s/{token}?k&folder` | без входа: оформление портала, кто передал, срок; содержимое папки (подпапки — только внутри общей), файл или страница; `locked: true`, пока не введён пароль |
| `POST /api/public/s/{token}/unlock {password}` | ключ `k` для остальных запросов |
| `GET /api/public/s/{token}/download/{file}?k`, `…/zip?k&folder`, `…/view/{file}?k` | скачать файл из общей области, архив, настройки просмотрщика ONLYOFFICE |

## 8ц. Визуальный редактор базы знаний (итерация 27, F9)

Миграция `0027_kb_editor.sql`: у `kb_pages` — `content` (HTML), `version`, `pinned`, `archived_at`, `archived_by`; таблицы `kb_page_versions` (история) и `kb_files` (картинки и файлы страниц). Бэкенд: `src/kb.rs`, очистка HTML и перевод Markdown — `src/kb_html.rs` (ammonia, pulldown-cmark). Фронтенд: TipTap 3 — `lib/kb/KbEditor.svelte`, `KbView.svelte`, `KbHistory.svelte`, `extensions.ts`, общие стили текста `content.css`.

### Редактор (вариант A «как в Word», решение заказчика)
- Панель: отмена и повтор; тип блока (обычный текст, заголовки 1–3, цитата, код); жирный, курсив, подчёркнутый, зачёркнутый; цвет текста и цвет фона (по 8 приглушённых цветов, видны в светлой и тёмной схеме); маркированный и нумерованный список, чек-лист; таблица (вставка, строки и столбцы, объединение, заголовок, удаление); картинка; файл; ссылка; ссылка на страницу базы; цитата, разделитель, «очистить форматирование».
- «/» в начале строки — меню вставки с поиском (заголовки, списки, чек-лист, таблица, картинка, файл, ссылка на страницу, цитата, код, разделитель).
- Вставка из Word и буфера сохраняет заголовки, списки, таблицы, жирный и цвет; лишние стили отбрасываются. Картинки вставляются из буфера или перетаскиванием, файлы — перетаскиванием.
- Ctrl+S — сохранить; при уходе со страницы с несохранёнными правками — предупреждение.
- Картинки (PNG, JPG, GIF, WEBP) показываются в тексте; остальные файлы — карточкой «имя · размер · автор · дата» со скачиванием. До 50 МБ на файл, учитываются в квоте хранилища портала.
- Сервер чистит HTML: только теги и атрибуты редактора, из стилей — цвет, фон, выравнивание, ширина столбцов; картинки — только из файлов базы знаний; без скриптов и обработчиков.

### Страница
- Шапка: «Создана <дата>, <кто> · Обновлена <дата>, <кто>»; аватары тех, кто сейчас смотрит страницу (обновление раз в 20 секунд, исчезают через 45 секунд без сигнала).
- **Одновременная правка (решение — «Предупреждать»):** если страницу уже редактирует другой сотрудник, над редактором — предупреждение с его именем; при сохранении поверх чужих правок — вопрос «Сохранить поверх?».
- **Закрепление:** закреплённые страницы — отдельным блоком вверху дерева (общий для портала).
- **История (простая, решение заказчика):** каждое сохранение с изменениями — новая версия (кто, когда, размер); просмотр любой версии и «Восстановить» (текущая тоже остаётся в истории). Хранится 100 последних версий страницы.
- **Архив вместо удаления:** «В архив» убирает страницу с вложенными; ссылка «Архив» под деревом — список, «Восстановить» (вместе с вложенными, на прежнее место или в корень, если родитель остался в архиве) и «Удалить навсегда» (с файлами страницы). Права — автор или администратор. Архивные страницы не видны в дереве, поиске и по ссылкам для внешних.
- Ссылки для внешних (раздел 8х) показывают страницу с картинками и карточками файлов; файлы скачиваются через ссылку.
- Перевод старых страниц: при запуске бэкенда страницы без HTML переводятся из Markdown (заголовки, списки, чек-листы, таблицы, переносы строк) с записью версии 1.

### Аудит
`kb.page_created`, `kb.page_archived`, `kb.page_restored`, `kb.page_deleted` (навсегда), `kb.version_restored`.

### API
| Метод и путь | Назначение |

## 8ч. Отчёты CRM (итерация 28, B11)

Модуль `backend/src/crm/reports.rs`, миграция `0028_crm_reports.sql` (журнал этапов сделок `crm_deal_stage_log`). Интерфейс — вкладка «CRM → Отчёты» (`routes/crm/reports`), вариант A — одна сводная страница (решение заказчика).

### Что видно
- **Период:** месяц, квартал, год, прошлый год, произвольный (даты — по часовому поясу портала). Новые сделки считаются по дате создания, выигранные и проигранные — по дате закрытия.
- **Показатели:** новых сделок (и разница с предыдущим периодом той же длины); выиграно — число, сумма, средний чек; конверсия в договор — доля выигранных среди закрытых за период (и разница в п. п.); средний цикл выигранной сделки, дней; открытые сделки сейчас и их сумма с учётом вероятности этапов.
- **Воронка:** сделки, созданные за период, по этапам; сделка учитывается на каждом этапе до самого дальнего, которого достигла, выигранная — на всех; переход от этапа к этапу в процентах, сумма на этапе.
- **Выиграно и проиграно по месяцам** (суммы): месяцы периода, не меньше шести (заканчивая последним месяцем периода) и не больше 24.
- **Ответственные:** новых, выиграно, сумма выигранных, конверсия, открытых; тем, кто видит раздел «Финансы», — «Поступило» (проведённые поступления за период по счетам сделок и по проектам, созданным из сделок) и «Долг клиентов» (неоплаченные счета сделок на сегодня, ссылка в «Финансы → Дебиторка»); строка «Итого».
- **Причины отказов:** проигранные за период сделки по причинам (без учёта регистра и пробелов), «Без причины» — в конце.
- Любое число открывает список сделок за ним (до 500, крупные первыми) со ссылками на сделки.
- **Выгрузка в XLSX:** листы «Сводка», «Воронка», «По месяцам», «Менеджеры» (деньги — только с правами на финансы), «Причины отказов», «Сделки» (созданные или закрытые за период, с фильтром).
- При переносе сделки в «Проиграна» предлагаются причины, которые уже встречались (одним нажатием), — так отчёт группирует их точнее; в карточке сделки — подсказки в поле «Причина проигрыша».

### Кто видит
- Менеджер CRM и администратор — все сделки портала, с выбором ответственного (или «Без ответственного»).
- Пользователь CRM — только сделки, где он ответственный; выбор ответственного не показывается.
- Без доступа к CRM — 403.

### Журнал этапов
Каждое попадание сделки на этап (создание, перенос) записывается в `crm_deal_stage_log`. Для существующих сделок журнал восстановлен миграцией по записям истории «Создана сделка … на этапе …» и «Этап сделки …: A → B»; если этапы переименовывали, учитывается хотя бы текущий этап.

### API
| Метод и путь | Назначение |
|---|---|
| `GET /api/crm/reports?from&to&responsible_id` | `{ kpi, funnel, months, managers, totals, reasons, money, can_filter, prev_from, prev_to }`; `responsible_id` — только для менеджеров, `none` — без ответственного |
| `GET /api/crm/reports/deals?…&set=new\|won\|lost\|open\|funnel\|reason&stage_id&reason&manager` | сделки за числом отчёта: `{ deals, count, amount }` |
| `GET /api/crm/reports.xlsx?from&to&responsible_id` | отчёт в Excel |
| `GET /api/crm/lost-reasons` | до 12 причин проигрыша, частые первыми |

## 12. Развёртывание на сервере офиса

Файлы: `docker-compose.yml` (весь комплект), `docker-compose.prod.yml` (HTTPS на домене), `docker-compose.local.yml` (тот же домен на компьютере разработчика), `deploy/Caddyfile` (обратный прокси), `scripts/backup.sh` (резервные копии), `scripts/start.cmd`, `scripts/hosts-local.cmd`, `scripts/trust-local-cert.cmd`, `scripts/backup-now.cmd`, `scripts/restore.cmd` (команды для Windows), `scripts/onlyoffice_live_test.py` (проверка ONLYOFFICE).

### Три режима запуска
| Команда | Где | Адрес | Сертификат |
|---|---|---|---|
| `scripts\start.cmd` | любой компьютер | `http://localhost:8080`, документы `:8081` | нет (HTTP) |
| `scripts\start.cmd local` | компьютер разработчика (сейчас — основной режим) | `https://cloud-project.online`, `https://docs.cloud-project.online` | локальный центр сертификации Caddy |
| `scripts\start.cmd prod` | сервер офиса | те же адреса из интернета | Let's Encrypt |

Режимы `local` и `prod` отличаются только источником сертификата (`CADDY_TLS=internal` / `acme`) и разрешением создавать порталы: всё остальное (HTTPS, `COOKIE_SECURE=true`, адреса, прокси) одинаково, поэтому на компьютере разработчика проверяется ровно то, что потом заработает на сервере.

### Локальный режим (компьютер разработчика)
Один раз на компьютере:
1. `scripts\hosts-local.cmd` **от имени администратора** — добавляет в файл `hosts` строки `127.0.0.1 cloud-project.online` и `127.0.0.1 docs.cloud-project.online` (с пометкой `# cloud-project-local`; `hosts-local.cmd remove` удаляет их).
2. `scripts\start.cmd local` — запуск. Порты 80 и 443 компьютера должны быть свободны (их могут занимать IIS, другие веб-серверы).
3. `scripts\trust-local-cert.cmd` — добавляет корневой сертификат локального центра Caddy в хранилище Windows текущего пользователя (Windows спросит подтверждение). После этого Edge и Chrome открывают `https://cloud-project.online` без предупреждений; Firefox — при `security.enterprise_roots.enabled = true`. Корневой сертификат хранится в томе `caddy-data`: если том удалить, шаг 3 нужно повторить.

Далее — просто `scripts\start.cmd local`. Создавать порталы в этом режиме можно (`SIGNUP_ENABLED`). Домен в этом режиме открывается только на этом компьютере; другим сотрудникам офиса он станет доступен в режиме `prod` на сервере. При переходе на сервер офиса выполнить `scripts\hosts-local.cmd remove`, иначе этот компьютер продолжит открывать свой локальный портал.

### Состав
| Сервис | Назначение |
|---|---|
| `db` | PostgreSQL 16 |
| `backend` | API; проверка готовности — `workhub-server healthcheck` (запрос к `/api/health`) |
| `web` | nginx: интерфейс и прокси `/api` на бэкенд |
| `onlyoffice` | ONLYOFFICE Docs, версия закреплена (`ONLYOFFICE_VERSION`, по умолчанию 9.2.1); проверка готовности — `/healthcheck` |
| `backup` | Ночные резервные копии в папку `./backups` |
| `caddy` | Только в `docker-compose.prod.yml`: HTTPS с сертификатами Let's Encrypt |

Имя проекта Docker Compose — `cloud-project`, поэтому тома (`cloud-project_db-data`, `cloud-project_blobs` и др.) те же, что при прежнем запуске из папки `CLOUD-PROJECT`.

### Домен и HTTPS
- Портал — `https://cloud-project.online`, сервер документов — `https://docs.cloud-project.online` (меняются переменными `PORTAL_DOMAIN`, `DOCS_DOMAIN`).
- Caddy сам получает и продлевает сертификаты Let's Encrypt (проверка HTTP-01). Нужно:
  1. постоянный «белый» IP-адрес офиса;
  2. DNS-записи типа A: `cloud-project.online` и `docs.cloud-project.online` → этот IP;
  3. на роутере проброс TCP 80 и 443 (и UDP 443 для HTTP/3) на сервер;
  4. по желанию в `.env` — `ACME_EMAIL` (учётная запись Let's Encrypt; по умолчанию admin@cloud-project.online).
- Внутри офиса домен должен открываться тоже. Если роутер не умеет «петлю» NAT (обращение из локальной сети на свой внешний IP), на роутере или в локальном DNS направьте оба имени на локальный адрес сервера.
- Режим prod: `COOKIE_SECURE=true`, `PUBLIC_URL`/`DOCS_PUBLIC_URL` на домены, создание порталов выключено независимо от `SIGNUP_ENABLED` в `.env` (для создания первого портала один раз запустить с `PROD_SIGNUP_ENABLED=true`), порты 8080/8081 открыты только на самом сервере (`127.0.0.1`), снаружи — только через Caddy.
- Адрес клиента для защиты входа: Caddy передаёт его в `X-Forwarded-For`, nginx берёт его только от адресов из `REAL_IP_FROM` (в prod — сеть Docker `172.16.0.0/12`; без прокси никому не доверяет). На Docker Desktop для Windows входящие соединения могут приходить с одного адреса шлюза — тогда ограничения входа считаются общими для всех; для сервера лучше Linux.
- Поток уведомлений (`/api/notifications/stream`) проксируется без сжатия и буферизации; WebSocket сервера документов Caddy пропускает сам.
- **Обновление портала в открытых вкладках** (итерация 29): `index.html` (он же ответ на любой адрес страницы) и `/_app/version.json` отдаются с `Cache-Control: no-cache`, файлы `/_app/immutable/` — на год. Открытая вкладка раз в минуту сверяет версию сборки (`version.pollInterval` в настройках SvelteKit, `vite.config.ts`) и после пересборки показывает внизу плашку «Портал обновлён» с кнопкой «Обновить» (`UpdateBanner.svelte`). До итерации 29 вкладка, открытая до пересборки, могла показывать старую версию (вероятная причина того, что у заказчика «не отображалась» карточка сотрудника).
- **Защитные заголовки страниц** (nginx, итерация 29): `X-Frame-Options: SAMEORIGIN` и `Content-Security-Policy: frame-ancestors 'self'; object-src 'none'; base-uri 'self'` (портал нельзя встроить в чужой сайт), `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin`, `Permissions-Policy` без камеры, микрофона, геолокации и оплаты. Полная CSP для скриптов не включена: редактор загружает `api.js` с адреса сервера документов, который задаётся в `.env`. HSTS добавляет Caddy. Проверка — `scripts/web_headers_test.py` (`WEB=http://localhost:8080`).

### Порядок запуска на сервере
1. Установить Docker (на Linux — Docker Engine с плагином compose; на Windows — Docker Desktop с автозапуском, без сна и гибернации).
2. Скопировать папку проекта; создать `.env` из `.env.example`, задать секреты (`openssl rand -hex 32`).
3. `scripts\start.cmd prod` (Windows) или `docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build`.
4. Открыть `https://cloud-project.online`, создать портал (при `PROD_SIGNUP_ENABLED=true`), затем убрать эту строку из `.env` и повторить шаг 3.
5. Проверить ONLYOFFICE: `python scripts/onlyoffice_live_test.py --tenant <портал> --email <почта>` (на сервере — адреса по умолчанию `http://localhost:8080` и `:8081`; снаружи — `--portal https://cloud-project.online --docs https://docs.cloud-project.online`).
6. Сделать резервную копию вручную (`scripts\backup-now.cmd`) и убедиться, что она появилась в `backups`.

### Резервные копии
- **Расписание задаётся в портале** (итерация 29): час — в разделе «Резервные копии» (таблица `backup_settings`, миграция 0030; одна строка на сервер), часовой пояс — тот же, что у портала `BACKUP_PORTAL` («Администрирование → Портал», `tenants.timezone`). `BACKUP_HOUR` и `TZ` из `.env` — только значения по умолчанию (старая база, нет портала). Сервис читает настройки из базы каждую минуту, поэтому изменения действуют без перезапуска. Имя пояса из базы перед подстановкой в SQL проверяется (только буквы, цифры, `/ _ + -`).
- Сервис `backup` раз в минуту проверяет время по часам PostgreSQL в поясе портала и делает копию:
  - в назначенный час **или позже в тот же день**, если за сегодня копии ещё нет (компьютер был выключен в назначенный час — копия будет сделана после включения);
  - **в любое время**, если последней готовой копии больше 26 часов (например, компьютер работает только днём, а час копии — ночью);
  - после неудачной попытки следующая — не раньше чем через `RETRY_SECS` (по умолчанию час).
- Он же выполняет заявки «Сделать копию сейчас» из портала (файл `REQUEST`), отмечается в `STATUS` и записывает итог последней попытки в `LAST_RESULT`.
- Каждый шаг копирования проверяется отдельно (подключение к базе, `pg_dump`, архив файлов, проверка дампа); при ошибке копия не помечается готовой, а текст ошибки виден в разделе «Резервные копии».
- Копия — папка `backups/cloud-project-ГГГГ-ММ-ДД_ЧЧММ`: `db.dump` (pg_dump, формат custom), `files.tar.gz` (все версии документов, логотипы и прочие файлы портала), `COMPLETE` (пишется последним: время и размеры). Дамп сразу проверяется чтением (`pg_restore -l`).
- Хранится `BACKUP_KEEP_DAYS` дней (по умолчанию 14); незавершённые копии удаляются через сутки. Папку можно вынести на другой диск (`BACKUP_PATH`); копировать её на внешний носитель или в облако — отдельно.
- Восстановление: `scripts\restore.cmd ИМЯ` — останавливает портал, заменяет базу и файлы содержимым копии, запускает портал. Без остановки бэкенда восстановление отказывается работать (база занята).
- `.env` в копию не входит: храните его отдельно. Без того же `APP_SECRET` не расшифруются сохранённые пароли почты, без `DOCS_JWT_SECRET` — потребуется перенастроить сервер документов (он берёт секрет из того же `.env`).
- **Раздел «Администрирование → Резервные копии»** (итерация 20) — виден администраторам портала, указанного в `.env` как `BACKUP_PORTAL` (адресное имя портала, например `partner-garant`). Копия содержит данные всех порталов сервера, поэтому администраторы других порталов раздела не видят (сервер отвечает 404); без `BACKUP_PORTAL` раздела нет. Папка копий подключена к сервису `backend` (`BACKUP_DIR=/backups`); сам бэкенд копий не делает.
  - **Состояние:** «работает» или «требует внимания»; последняя готовая копия и её размер; связь с сервисом (сервис «молчит», если не отмечался больше 10 минут); число хранящихся копий; расписание и срок хранения.
  - **Время ночной копии** (итерация 29): выбор часа 00:00–23:00 с кнопкой «Сохранить», рядом — пояс портала со ссылкой «изменить» на «Портал» и пояснение про догоняющую копию. Изменение пишется в журнал (`backup.settings_changed`). В «Портал → Часовой пояс» администратору системного портала показано, что по этому поясу делаются и резервные копии.
  - **Предупреждения:** папка копий недоступна бэкенду; сервис не отвечает; готовых копий нет или последняя старше 26 часов; последняя попытка завершилась ошибкой (с текстом ошибки).
  - **«Сделать копию сейчас»** оставляет заявку `REQUEST` (кто и когда); сервис берёт её в течение минуты. Повторное нажатие до выполнения новой заявки не создаёт. Пока заявка ждёт или копия пишется, страница обновляется каждые 10 секунд.
  - **Список копий** (новые сверху): дата и время, состояние («Готова», «Создаётся…» — папка без `COMPLETE` моложе 3 часов, «Не завершена»), размеры базы и файлов, имя с кнопкой копирования.
  - **Скачивание** готовой копии: `db.dump` и `files.tar.gz` отдельно, потоком с диска (архив может весить гигабайты; в `nginx.conf` для этих адресов — регулярное выражение по `…/db.dump` и `…/files.tar.gz` — отключена буферизация; префиксный блок со слешем на конце не годится: nginx отвечал бы на адрес списка редиректом). Адреса API раздела — `/api/admin/reserve…`, без слова «backup»: блокировщики рекламы в браузере обрывают запросы с ним (так было у заказчика). Каждое скачивание пишется в журнал (`backup.downloaded`), заявка — `backup.requested`.
  - **Восстановление** со страницы не выполняется (портал на это время останавливается): в разделе — инструкция и команда `scripts\restore.cmd ИМЯ` для последней копии с кнопкой копирования.

  | Метод и путь | Назначение |
  |---|---|
  | `GET /api/admin/reserve` | Состояние сервиса, предупреждения, список копий |
  | `POST /api/admin/reserve/now` | Заявка «Сделать копию сейчас» |
  | `PATCH /api/admin/reserve/settings` | Час ночной копии `{hour: 0–23}`; ответ — состояние раздела (`hour`, `timezone`) |
  | `GET /api/admin/reserve/{name}/{db.dump\|files.tar.gz}` | Скачать часть готовой копии |

  `GET /api/auth/me` содержит `backups: true`, если пользователю доступен раздел.
- Проверено: копия рабочей базы и файлов восстановлена в чистую базу, бэкенд на восстановленной копии запускается, вход и скачивание документа работают, файлы совпадают побайтно.
