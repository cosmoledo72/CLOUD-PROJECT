## Как перенести работу в новый проект

1. Создайте проект Claude, например «WorkHub / CLOUD-PROJECT».
2. Загрузите в знания проекта (Project knowledge) три файла из `D:\PROGRAMS\CLOUD-PROJECT\docs`:
   - `CHAT_LOG.md` — этот журнал;
   - `PLAN.md` — сводный план работ и дорожная карта;
   - `SPEC.md` — спецификация и API.
3. Вставьте в инструкции проекта (Project instructions) текст из раздела «Инструкции для проекта» ниже.
4. Первым сообщением в новом чате — текст из раздела «Первое сообщение».
5. Для работы с кодом в чате должна быть подключена папка `D:\PROGRAMS\CLOUD-PROJECT` (через приложение Claude на компьютере).

## О проекте

- **WorkHub** — многопользовательский (multi-tenant) SaaS-аналог ONLYOFFICE CommunityServer для инженерного бюро «ПАРТНЕР-ГАРАНТ».
- **Стек:** бэкенд Rust (axum 0.8, sqlx 0.8, PostgreSQL 16), фронтенд SvelteKit 2 / Svelte 5 (adapter-static), редактор документов ONLYOFFICE Docs. Иконки — Lucide (`@lucide/svelte`), Markdown базы знаний — `marked` + `dompurify`.
- **Название:** с 11.11.2026 проект называется **CLOUD-PROJECT** (прежнее рабочее название — WorkHub, оно пока остаётся в коде и интерфейсе).
- **Папка проекта:** `D:\PROGRAMS\CLOUD-PROJECT` (Windows). На рабочей машине установлены Rust, PostgreSQL, Docker и WSL.
- **Документы:** план работ — `docs/PLAN.md`, спецификация — `docs/SPEC.md`, запуск и тесты — `README.md`.

## Договорённости

- Общение в чате — на русском; комментарии и описания в коде — на английском.
- Файл `.env` в корне проекта не трогать.
- Перед записью файлов в папку сверять их контрольные суммы с последней доставленной версией, чтобы не затереть ручные правки; после записи — проверять, что дошла новая версия (однажды запись положила старую копию файла).
- Новые разделы делались в «базовых версиях» с возможностью доработки.

## Как запустить локально

1. PostgreSQL 16 с базой из `.env`.
2. Бэкенд: в `backend` — `cargo run` (миграции применяются автоматически при старте).
3. Фронтенд: в `frontend` — `npm install`, затем `npm run dev` (http://localhost:5173, `/api` проксируется на :8080).

После обновления файлов: перезапустить бэкенд (если менялся Rust или миграции) и обновить страницу; при новых npm-пакетах — `npm install`.

### Итерация 20 (11.11.2026). Раздел «Резервные копии»
Вопрос заказчика: где резервное копирование и восстановление? - `docker-compose.yml`: папка копий подключена к `backend`, переменные `BACKUP_PORTAL`, `BACKUP_DIR`, `BACKUP_HOUR`, `BACKUP_KEEP_DAYS`; `.env.example` — строка `BACKUP_PORTAL`.
- Бэкенд `backups.rs`: состояние, список, заявка, потоковое скачивание; `nginx.conf` — без буферизации для скачивания копий.
- Страница «Администрирование → Резервные копии» (группа «Безопасность»).
- Исправление после проверки у заказчика: раздел показывал «Failed to fetch». Причина — блок `location /api/admin/backups/` в `nginx.conf`: префикс со слешем на конце заставляет nginx отвечать на `/api/admin/backups` (без слеша) редиректом 301, и запрос списка ломался. В облачной копии ошибка не проявлялась — там вместо nginx работает прокси vite. Блок заменён регулярным выражением, которое ловит только адреса скачивания.
- Второе исправление: по логам nginx запрос списка со страницы раздела до сервера не доходил вовсе — его обрывал браузер (расширение-блокировщик по слову `backups` в адресе), при этом прямой переход по адресу работал. Адреса API раздела переименованы в `/api/admin/reserve…`. Ошибка сети в портале теперь показывается по-русски с подсказкой про обновление страницы и расширения браузера вместо «Failed to fetch».
